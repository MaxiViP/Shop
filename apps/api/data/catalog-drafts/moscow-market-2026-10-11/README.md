# Импорт стартового каталога в Shop

Ревизия 2, 11 октября 2026 года. 114 товаров. Пользователь выбрал точку `vegetables-fruits-east` и разрешил предварительные цены с последующим редактированием в админке.

## Что изменено

- sellerPrice заполнен для всех 114 позиций, в целых копейках, ДО сервисной наценки.
- marketPointSlug = vegetables-fruits-east; название из docs/market-map.md: «Овощи и фрукты — правый ряд».
- Окончательные предложенные slug начинаются с vegetables-fruits-east-. catalogKey сохраняет идентичность; previousSlug нужен для поиска совпадений с первой версией.
- Имена будущих фото обновлены до окончательных slug.webp. Фото ещё не созданы.
- Все цены имеют priceStatus=ESTIMATED. Это разрешённые пользователем стартовые цены, а не SOURCE/AUDITED котировки продавца.
- priceReference сохраняет первоначальное исследование. priceSelection объясняет выбранную стартовую цену и замену отсутствующего западного ориентира.
- Начальные цены округлены к ближайшим 5 ₽. Формула показа цены: существующий customerPrice(sellerPrice) с +10%. В JSON customerPricePreviewKopecks — только пример, не поле Product.price.
- Новые товары подготовлены с active=false; включить выбранные позиции можно в админке. Подтверждённого остатка и ежедневного наличия нет.

## Основа цен

Западный ориентир — Дорогомиловский рынок, Москва, Можайский Вал, 10, через сторонний справочник Restorandia. Прямой сайт поставщика не удалось прочитать. Справочник даёт приблизительные цены «от», а не гарантированную оферту; даты его снимков и подписи свежести сохранены в источниках.

- WESTERN_DIRECTORY_ESTIMATE: 57 позиций, сопоставленный вид и единица товара.
- WESTERN_GROUP_PROXY_ESTIMATE: 14 позиций, цена близкой товарной группы; точный сорт/обработка не подтверждены. Пример: красные яблоки как стартовый ориентир Фуджи.
- MOSCOW_REFERENCE_FALLBACK_ESTIMATE: 43 позиций, прежняя московская котировка, поскольку сопоставимой западной нет. Не считать наблюдением цены на западе Москвы.

Нельзя считать пучок неизвестной массы равным 100 г или пересчитывать цену фрукта за штуку в килограмм без массы. Нулевые цены справочника не использованы. Для ягод выполнен пересчёт к указанной упаковке: клубника 1200 ₽/500 г → стартовые 600 ₽/250 г → 660 ₽ с нашей наценкой. Фасовка 250 г — подготовленная карточка, не подтверждённая фасовка источника.

Круглогодичность остаётся оценкой: 75 кандидатов в ядро и 39 позиций переменных поставок. Истории наличия все 12 месяцев нет. Предыдущие ссылки, descriptions, категории и исключённые сезонные позиции сохранены.

## Адаптер и запуск

Адаптер находится в `apps/api/data/catalog-import/`. Единственный вход товаров — `shop-import.json`; исследовательский `catalog-all.json` и четыре части повторно не импортируются. Prisma schema не менялась: действующие поля и enum уже поддерживают необходимые единицы.

Команды из корня репозитория в Windows PowerShell:

```powershell
pnpm.cmd --filter api catalog:import --dry-run
pnpm.cmd --filter api catalog:import --apply
```

`pnpm.cmd` обходит ограничение PowerShell на запуск `pnpm.ps1`. В других оболочках можно использовать `pnpm` с теми же аргументами. Подключение берётся из `apps/api/.env` / `DATABASE_URL`; CLI принимает только loopback-адрес PostgreSQL и учитывает параметр `schema`. Пароли в отчёты не попадают.

Каждый запуск сначала проверяет весь файл. Dry-run использует read-only serializable транзакцию. `--apply` повторяет dry-run и заново выполняет сопоставление в отдельной serializable транзакции записи; при ошибке откатываются и товары, и новая категория. Отсутствующая торговая точка, неоднозначные совпадения и несовместимые единицы/фасовки блокируют запись всего набора. При недоступной БД отчёт содержит результаты проверки файла и `databaseMatched: false`, процесс завершается с кодом 1.

Категории разрешаются по slug или однозначному совпадению названия. Только отсутствующую `berries` разрешено создать как «Ягоды». Торговая точка разрешается по существующему slug и не создаётся. Совпадения товаров проверяются по новому slug, предыдущему slug и названию с сохранением сорта, единицы, базы цены и массы упаковки; товары другого продавца не объединяются.

Компактный JSON не содержит `catalogKey`, `previousSlug` и `netWeightGrams`. Адаптер получает ключ из суффикса slug, предыдущий slug — из префикса ревизии 1 `moscow-market-`, массу PACK — из явно указанной фасовки в названии. Эти метаданные сохраняются в отчётах и `photo-map.json`, но не передаются в strict `productSchema`. Масса пучка не выдумывается. Неуточнённые картофель и авокадо не объединяются с конкретными сортами автоматически; разные единицы продажи остаются отдельными карточками.

Для существующих товаров заполняются только отсутствующее описание, пустая привязка к точке и отсутствующий источник. Цены, `priceStatus` (включая ESTIMATED/SOURCE/AUDITED), названия, slug, единицы, количества, активность и изображения сохраняются. Новые товары получают исходные описания, фасовки, шаг, минимум и порцию, `price = sellerPrice`, `priceStatus = ESTIMATED`, `active = false`. Сервисная наценка применяется существующим backend только при расчёте цены покупателя.

Полные планы всех 114 позиций: `reports/dry-run.json` и `reports/apply.json`. `reports/pre-apply.json` содержит последний dry-run перед записью. `photo-map.json` связывает `catalogKey` с фактическими ID, slug и именами будущих файлов; при подготовке фото использовать его поверх предложенных имён из `photo-briefs.json`. URL новых изображений не добавляются.
