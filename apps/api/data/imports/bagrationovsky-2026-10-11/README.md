# Подготовка данных Багратионовского рынка

Данные используются как исследовательские сведения. Подготовлена файловая очередь с 16 кандидатами магазинов и 168 товарными записями: 128 наблюдавшимися предложениями московского онлайн-каталога МясБерри и 40 позициями ассортимента производителя Былинкино. Все записи скрыты от покупателей и заказа. Запись в рабочую БД и публикация не выполнялись.

## Команды

Из корня репозитория в Windows PowerShell:

```powershell
# Проверка всех исходных JSON, read-only сверка с локальной БД и предварительный просмотр.
pnpm.cmd --filter api bagrationovsky:import --dry-run

# Сохранение только файловой очереди; БД используется исключительно для чтения.
pnpm.cmd --filter api bagrationovsky:import --prepare

# Проверка повторной подготовки с отдельным отчётом.
pnpm.cmd --filter api bagrationovsky:import --prepare --report=data/imports/bagrationovsky-2026-10-11/reports/repeat-prepare.json

# Проверка файлов без подключения к БД.
pnpm.cmd --filter api bagrationovsky:import --dry-run --offline
```

`pnpm.cmd` позволяет запускать команду при запрете PowerShell на исполнение `pnpm.ps1`; в других оболочках подойдёт `pnpm`. Подключение для сверки берётся из `apps/api/.env` / `DATABASE_URL`. CLI сверяется только с локальной PostgreSQL, учитывает `schema` и использует read-only транзакцию. При недоступной БД проверка файлов и подготовка очереди доступны, отчёт явно содержит `databaseMatched: false` и предупреждение о невыполненной сверке. Пароли не выводятся.

Дополнительные аргументы: `--queue=path.json`, `--report=path.json`; относительные пути считаются от `apps/api`. `--apply` отклоняется: команды записи в БД у этого адаптера нет. Исходные файлы и пояснения защищены от случайного выбора в качестве выходных файлов.

## Очередь, цены и единицы

Очередь: `prepared/import-queue.json`. Полные отчёты:

- `reports/preview.json` — первоначальный dry-run для всех магазинов и 168 товарных записей;
- `reports/prepare.json` — первая подготовка файловой очереди;
- `reports/repeat-prepare.json` — повторная подготовка;
- `reports/verification.json` — проверка неизменности БД и очереди.

Цена источника МясБерри хранится в `products[].source.referencePrice.amountKopecks`, отдельно от `products[].sale.confirmedPriceKopecks`, который остаётся `null`. Вместе с ней сохраняются `scope = MOSCOW_OFFICIAL_ONLINE_CATALOG_REFERENCE`, URL карточки и страницы наблюдения, `checkedOn`, исходный текст цены и количество ценовой базы. Например, 693 ₽ / 500 г записаны как 69 300 коп. за 500 граммов. Наценка и пересчёт к килограмму не выполняются.

Ценовая база нормализована в граммы: исходные 1 кг становятся `unit = GRAM`, `priceQty = 1000`; 300/400/450/500/600/800 г сохраняют свою массу. Исходные quantity, unit и текст единицы также сохранены. Проверено соответствие массы единице, копеек рублям и числовой цены исходному тексту. Денежное преобразование использует целочисленную арифметику.

Масса ценовой базы не считается массой упаковки: `netWeightGrams` остаётся `null`. Единица продажи рыночной точки, шаг, минимум и порция тоже остаются неизвестными. SKU, описание и наличие не придуманы. Для Былинкино цена, единица и масса сохраняются как `null`; одинаковые названия сыров из разного молока имеют разные исследовательские ключи.

Все 12 групп возможных дублей проверены: перечисленные исходные ID существуют, нормализованные названия совпадают, наблюдавшиеся цены и массы ценовой базы одинаковы. Это не подтверждает одинаковый SKU. Обе карточки каждой группы сохранены; их URL, цены, массы и исходные ID приведены в `reports/preview.json`.

Наценка этой подборки остаётся несогласованной: `sale.markupPercent = null`. Адаптер не вызывает `customerPrice()` и не переносит прежнюю договорённость для `vegetables-fruits-east`. Существующая логика расчёта цен магазина сохраняется.

## Повторная подготовка и ручные изменения

Для МясБерри ключ очереди строится из поставщика и `sourceItemId`; этот ID не считается SKU или ID Product. Для Былинкино используется хеш явно указанной категории, названия и варианта молока; этот технический ключ также не является артикулом. Для магазинов используется `researchKey`, который не считается slug или ID MarketPoint.

Повторный запуск переиспользует все записи и сохраняет `review`: статус, явно выбранные ID, подтверждённый оператором SKU, заметки и дату проверки. Поля источника и цены продажи не следует вручную подменять. При изменении источника сохраняется прежняя запись, а отчёт показывает `review_source_change` и `incomingSource` для сравнения. Исчезнувшие из источника записи сохраняются для проверки. Невалидная очередь блокирует перезапись.

Идентичная повторная подготовка дала 0 новых магазинов, 0 новых товаров, 16 сохранённых магазинных и 168 сохранённых товарных записей. Содержимое очереди и время её изменения остались прежними. Запись выполняется через временный файл и атомарное переименование; изменение очереди оператором во время предварительной проверки обнаруживается и блокирует перезапись.

Подтверждённая цена существующего товара редактируется обычной админкой `/admin/products/:id` через `PATCH /api/admin/products/:id`, `AdminProductsCtrl -> AdminProductsService -> Prisma`, с действующим `AdminGuard`. Если оператор явно указал Product ID в `review.productId`, предпросмотр читает его текущую цену в `linkedProduct`. Справочная онлайн-цена хранится отдельно и не заменяет Product.price. Тест проверяет изменение цены через настоящий административный сервис и её сохранение при повторной подготовке.

## Механизм для дальнейшей интеграции

`MarketPoint.isPublished = false` и `Product.active = false` позволяют скрыть подготовленные каталожные записи. Для этих исследовательских данных требуется дополнительный механизм: обязательный `Product.price` положителен, параметры заказа обязательны, отдельного хранилища справочных цен и связи с исследовательскими ID в текущей Prisma schema нет. По условию задачи использована отдельная файловая очередь; ложная цена для заполнения Product не создавалась.

Для переноса очереди в БД понадобится административный процесс проверки с отдельными черновиками, допускающими неизвестные значения, и справочными котировками: источник, дата проверки, регион/область действия, цена в копейках и ценовая база в граммах. Связь исследовательского ключа с MarketPoint/Product должна иметь уникальное ограничение и подтверждаться ADMIN после сверки вывески, павильона и SKU. Создание магазина должно повторно проверять существующие точки; названия и гипотезы сами по себе недостаточны.

После получения датированного прайса конкретной точки ADMIN вводит подтверждённую цену и параметры продажи через существующий административный сервис. Повторное обновление справочных котировок должно затрагивать только справочное хранилище, сохраняя ручной Product.price, активность и изображения. Допуск к витрине и заказу требует подтверждения наличия и явной политики наценки.

Текущий `customerPrice()` использует общий процент 10, а `settlementMode = NO_MARKUP` относится к распределению маржи. Перед публикацией этой подборки нужно согласовать и реализовать подходящую политику цены одинаково для каталога, корзины и снимков заказа. Текущая команда такой публикации не выполняет и не меняет существующие правила.
