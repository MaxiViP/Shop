# Shop

### Сборка и оплата товаров (PHASE 1)

Checkout создаёт заказ с **предварительной** стоимостью. Продавец вводит фактическое количество (для GRAM — показание весов, независимо от customer step); цена берётся из snapshot позиции. После завершения сборки фиксируется `finalSubtotal` и открывается оплата товаров и дополнительных услуг магазина. Доставка оплачивается отдельно: `deliveryPrice`/`finalTotal` сохранены для совместимости, но не входят в `OrderPayment.amount`.

В `/admin/settings` ADMIN задаёт допуск веса 0–50% (integer BPS, по умолчанию 1000 = 10%). Заказ сохраняет собственный snapshot допуска. Превышение блокирует завершение сборки до явного согласия покупателя на конкретный вес. Заказ без товаров к оплате нужно отменить либо продолжить сборку.

Оплата (PHASE 2.1): `AWAITING → PAID`. Покупатель переводит деньги без кнопки «Я оплатил». SELLER/ADMIN проверяет банк: для DELIVERY действие «Оплата получена — оформить доставку» сначала фиксирует PAID, затем вызывает доставку; сбой Яндекса не откатывает оплату. Для PICKUP есть отдельное «Оплата получена». До PAID нельзя отправлять/выдавать заказ. Возврат READY к сборке возможен при AWAITING до оформления доставки. Отмена PAID запрещена до отдельного refund workflow. `REPORTED` и защищённый owner/guest report endpoint сохранены только для старых клиентов; новый UI их не использует, REPORTED никогда не означает PAID.

В сборке staff может добавить `OrderExtra`: название, комментарий, целое количество и цену в копейках. Это не товар каталога и не OrderIssue: отдельного подтверждения покупателя нет. ACTIVE услуги входят в `finalSubtotal` и единственный `OrderPayment.amount`, доставка — отдельно. Покупатель видит услуги явно в окончательном расчёте перед оплатой. Исправление до оплаты: чат → вернуть к сборке → изменить/отменить услугу → завершить сборку заново. Отменённые строки сохраняются в истории. После PAID изменения запрещены.

Чат использует incremental polling, CUSTOMER справа, SELLER/ADMIN слева, SYSTEM по центру. Header показывает persisted communication unread отдельно для customer и staff (обновление каждые 10 секунд в видимой вкладке). Issues/SMS не прибавляются к этому счётчику. Открытый видимый чат отмечает прочитанными полученные сообщения.

В backend secrets задаются `PAYMENT_RECIPIENT_NAME`, `PAYMENT_PHONE`, `PAYMENT_BANK_NAME`, `PAYMENT_CARD_NUMBER`, `PAYMENT_SBP_LINK`, `PAYMENT_QR_IMAGE_URL` (в `.env.example` только пустые placeholders). Показываются лишь настроенные способы; ссылки/QR должны использовать HTTPS. QR предоставляется банком, приложение не генерирует банковский QR и не встраивает сумму в статичный QR. Реквизиты доступны только владельцу финализированного заказа, включая безопасную guest session, не через public runtimeConfig.

Миграция не помечает исторические заказы оплаченными и не меняет их суммы. Старые READY без payment можно явно вернуть к сборке и финализировать по новому flow; историческую оплату нельзя предполагать автоматически. Возвраты и восстановление потерянного Yandex claim остаются PHASE 3.

Интернет-магазин свежих продуктов с московского рынка: каталог, корзина, гостевой checkout, профиль покупателя, сборка заказов продавцом и интеграция с внешней доставкой.

### Согласование заказа (PHASE 2)

Превышение веса и отсутствие товара создают структурированную `OrderIssue`. Покупатель принимает конкретный вес, просит уменьшить, убирает товар или отменяет ещё не оплаченный заказ. Согласие привязано к версии: возврат строки в сборку аннулирует его. Замена предлагается из каталога со snapshot цены/количества и после принятия создаёт новую позицию; исходная остаётся в истории. Нерешённые вопросы блокируют финализацию.

На customer/staff detail есть чат (plain text, cursor pagination, polling только в активной вкладке), решения и unread. Гость использует прежнюю HttpOnly guest session. Ссылка на заказ сама по себе не даёт доступа; на другом устройстве понадобится вход по телефону и привязка заказа. Ожидание ответа настраивается ADMIN (1–120 минут, по умолчанию 10), затем staff видит предложение позвонить. Автоматических повторных SMS и определения browser presence нет.

`ACTION_REQUIRED` и `PAYMENT_READY` сохраняются в `OrderNotification` в той же транзакции, отправка выполняется после commit. Для каждого issue/version есть уникальный dedupe key; ручной повтор ограничен одной минутой. Сейчас реальный SMS-адаптер **не подключён**: статус `UNCONFIGURED`, никакой имитации отправки. Для запуска требуется выбрать провайдера, реализовать `OrderSmsProvider` (таймауты, подтверждённый результат отправки) и настроить backend `ORDER_SMS_ENABLED`, `ORDER_SMS_PROVIDER`, `ORDER_SMS_API_URL`, `ORDER_SMS_API_KEY`, `ORDER_SMS_SENDER`, `ORDER_SITE_URL` (HTTPS origin). Одних env недостаточно; OTP не изменён. Неопределённый результат `SENDING` нельзя автоматически переотправлять: сначала сверить с провайдером. Staff всегда может позвонить через `tel:`.

Проект развивается как production-oriented monorepo с отдельными Nuxt frontend и NestJS API.

- избранное: локально для гостя, в аккаунте для авторизованного пользователя и автоматическое объединение после входа;

- корзина;
- оформление заказа без регистрации;
- доставка и самовывоз;
- вход по номеру телефона и OTP без постоянного пароля;
- профиль и сохранённые адреса;
- история заказов;
- просмотр заказа по защищённому `publicId`;

- после входа по тому же номеру подходящие гостевые заказы связываются с аккаунтом.

### Продавец

Рабочее место продавца доступно ролям `SELLER` и `ADMIN`.

Order flow:

```text
NEW
→ CONFIRMED
→ ASSEMBLING
→ READY
→ DELIVERING
→ COMPLETED
```

Во время сборки продавец может:

- указать фактический вес/количество;
- отметить товар как `PICKED`;
- отметить товар как `MISSING`;
- вернуть ошибочно обработанную позицию обратно в `PENDING`;
- завершить сборку только после обработки всех позиций.

Финальная стоимость товаров рассчитывается backend по фактически собранному количеству.

### Доставка

Поддерживаются два провайдера:

- `YANDEX` — автоматическая интеграция с Yandex Delivery B2B API;
- `OTHER` — ручная внешняя курьерская служба.

#### Yandex Delivery

Backend умеет:

- рассчитывать актуальную стоимость доставки;
- создавать Yandex claim;
- принимать заявку;
- получать tracking URL;
- хранить внешний статус;
- автоматически синхронизировать активные доставки;
- переводить заказ в `DELIVERING`, когда курьер забрал заказ;
- автоматически переводить заказ в `COMPLETED` после успешной доставки.

Основные Yandex endpoints:

```text
POST /offers/calculate
POST /claims/create
POST /claims/info
POST /claims/accept
POST /claims/tracking-links
POST /claims/bulk_info
```

Активные Yandex-доставки синхронизируются backend примерно раз в 30 секунд. Polling работает без frontend и без обязательного callback.

Стоимость Yandex не рассчитывается приложением самостоятельно: source of truth — ответ Yandex API. Деньги внутри приложения хранятся как integer kopecks.

#### Other delivery

Для другой курьерской службы продавец вводит данные вручную.

Обязательно:

- имя курьера;
- телефон курьера;
- положительная стоимость доставки (в интерфейсе — рубли, API — целые копейки).

Необязательно:

- tracking URL;
- внешний ID.

Для нового `DELIVERY` стоимость доставки и полный итог неизвестны (`null`), пока staff не рассчитает Яндекс Доставку или не сохранит цену `OTHER`. Самовывоз имеет цену доставки `0`. `subtotal` хранит первоначальную стоимость товаров; после сборки `finalSubtotal` содержит фактическую стоимость. `total` и `finalTotal` включают известную цену доставки, а при неизвестной цене остаются `null`.

Quote Яндекса сохраняется как текущая предварительная стоимость. При бронировании его заменяет цена подтверждённой заявки; последующие изменения известной цены принимаются только из более нового `final_price`. Помимо активных заявок polling проверяет завершённые/отменённые заявки с `providerUpdatedAt` за последние 24 часа, чтобы получить отложенную окончательную стоимость. Callback и ручная синхронизация работают и за пределами этого окна.

Checkout запоминает имя получателя только после успешного создания заказа, отдельно для гостя и каждого аккаунта в localStorage. Профильное `User.name` не изменяется.

Самовывоз доступен в checkout без адреса покупателя: «Начать собирать сразу» сохраняет `PICKUP + deliveryAt = null`, «Ко времени» — выбранное будущее время. Ввод и отображение времени самовывоза — по Москве. Статус нового заказа остаётся `NEW`; подтверждение, сборку и выдачу выполняет сотрудник. В активной staff-очереди ASAP-самовывоз идёт первым (старые заказы раньше новых), остальные заказы — по запрошенному времени с прежним порядком DELIVERY.

Единственная точка самовывоза по умолчанию задана в `apps/web/nuxt.config.ts`. Её можно переопределить публичными переменными окружения Nuxt:

```dotenv
NUXT_PUBLIC_PICKUP_NAME="ТЦ «Багратионовский»"
NUXT_PUBLIC_PICKUP_ADDRESS="ул. Барклая, 10, Москва"
```

Название и адрес отображаются для самовывоза в checkout, деталях заказа и на странице успешного оформления.

Проверка времени самовывоза и сортировки без дополнительных зависимостей: `node --test apps/web/test/pickup.test.mjs`.

## Роли

### Admin v1

Общая форма входа автоматически запрашивает `POST /api/auth/method` после полного телефона и паузы 400 мс. Ответ содержит только `OTP` или `PASSWORD`: USER/SELLER продолжают входить по коду, настроенный административный номер — по паролю через существующий `/api/auth/admin/login`. Вход из магазина закрывает форму без перехода в админку. `/admin/login` сохранён. При смене номера поля и предыдущий метод сбрасываются, запоздавшие ответы игнорируются. Значения административных env не передаются во frontend.

`/api/auth/method` ограничен 15 запросами с socket IP за 5 минут и 300 запросами на процесс; лимит независим от admin login и не доверяет X-Forwarded-For. Ответ позволяет отличить способ входа для введённого номера, но не раскрывает наличие пользователя или роль. Проверки состояний формы: `node --test apps/web/test/auth-method.test.mjs`.

В `apps/api/.env` задайте `ADMIN_PHONE` (российский телефон) и `ADMIN_PASSWORD` (длинный уникальный пароль). Пример содержит только пустые значения; реальные credentials храните в локальном окружении или production secrets. При незаданных значениях административный вход закрыт.

Вход: `/admin/login`; товары и категории: `/admin/products`; пользователи: `/admin/users`. `POST /api/auth/admin/login` проверяет digest пароля через timing-safe comparison и выдаёт обычную HttpOnly session cookie. OTP остаётся для USER/SELLER; административный номер и ADMIN не могут войти через OTP. Проверка пароля не является подтверждением владения телефоном и не присваивает `verifiedAt`.

Единственный административный номер задаётся `ADMIN_PHONE`: AdminGuard каждый раз получает пользователя из Session и проверяет роль и номер. При успешном admin login в транзакции старые ADMIN теряют административную роль и сессии; прежние сессии USER/SELLER настроенного номера отзываются перед повышением. Если номер изменён в secrets, прежний ADMIN сразу теряет доступ после перезапуска. Через API можно менять только USER ↔ SELLER. Пользователи не удаляются.

Admin login ограничен 5 попытками с IP за 15 минут и 100 попытками суммарно на процесс; счётчики живут в памяти и сбрасываются при перезапуске. Для нескольких экземпляров API нужен общий rate limiter на reverse proxy. API не доверяет пользовательскому X-Forwarded-For. Production должен работать через HTTPS.

Фото: multipart `POST /api/admin/products/:id/images`, поле `file`, до 5 МБ, до 8 фото на товар. JPEG/PNG/WebP декодируются, проверяются (до 25 мегапикселей) и перекодируются sharp в WebP без исходных метаданных. SVG и анимация не принимаются. Файлы с UUID сохраняются в `apps/api/uploads/products` при запуске через pnpm; `UPLOAD_DIR` позволяет задать абсолютный каталог storage. В production каталог должен быть постоянным и резервироваться отдельно от БД. В БД хранится `/uploads/products/<uuid>.webp`; общий frontend helper использует origin `NUXT_PUBLIC_API_BASE`, сохраняя абсолютные URL.

Удаление фото/товара удаляет соответствующие строки и managed-файлы; файлы, использованные в снимках исторических заказов или другом ProductImage, сохраняются для истории. При ошибке filesystem после DB delete может остаться неиспользуемый файл; он не открывает доступ к произвольным путям. Товар можно скрыть без удаления. Категории с товарами или дочерними категориями удалить нельзя.

В development CORS допускает только HTTP localhost/127.0.0.1 с явно заданным портом. В production задайте `CORS_ORIGINS` — точные frontend origins через запятую (без завершающего `/`). Без значения cross-origin доступ закрыт. `PORT` по умолчанию 4001; `NUXT_PUBLIC_API_BASE` по умолчанию `http://127.0.0.1:4001/api`.

Admin API возвращает только бизнес-поля пользователей, статистику завершённых заказов, адреса и последние 10 заказов. Хеши сессий, OTP и другие auth secrets в административные ответы не включаются. Суммы неизвестных завершённых заказов показываются отдельно от суммы известных итогов.

После `pnpm build` дополнительный сквозной smoke: `pnpm --filter api exec node test/admin.smoke.mjs`. Скрипт требует локальную PostgreSQL из `DATABASE_URL` с правом CREATE SCHEMA; создаёт уникальную временную схему, применяет к ней существующие миграции, использует случайный временный пароль и свободные порты, проверяет API и авторизованный Nuxt SSR, затем удаляет только свои тестовые данные, фото и схему. Рабочая схема магазина не изменяется. Браузерные клики и мобильную компоновку нужно проверять отдельно.

```text
USER    покупатель
SELLER  продавец / сборщик
ADMIN   полный административный доступ + staff workflow
```

## Каталог и избранное

`GET /api/products` принимает `q`, `category`, `sort`, `page` и `limit` и возвращает объект `{ items, total, page, limit, pages }`. Для получения актуальных гостевых избранных также доступен ограниченный фильтр `ids`.

Серверное избранное защищено пользовательской сессией:

```text
GET    /api/favorites
POST   /api/favorites/:productId
DELETE /api/favorites/:productId
POST   /api/favorites/sync
```

Гостевое избранное хранит в `localStorage` только идентификаторы товаров. После успешного входа они добавляются в серверное избранное; локальные данные очищаются только после успешной синхронизации и повторной загрузки списка.

## Локальный запуск

### Требования

- Node.js `>=24 <25`
- pnpm `11.24+`
- Docker Desktop / Docker Engine

### 1. Установить зависимости

```bash
pnpm install
```

### 2. Запустить PostgreSQL

```bash
docker compose up -d
```

По умолчанию локальная база:

```text
host: 127.0.0.1
port: 5432
database: shop
user: shop
password: shop
```

### 3. Настроить API env

Создать:

```text
apps/api/.env
```

Минимальная конфигурация:

```dotenv
DATABASE_URL=postgresql://shop:shop@127.0.0.1:5432/shop?schema=public
AUTH_SECRET=replace-with-a-long-random-secret
```

### 4. Применить миграции

```bash
cd apps/api
pnpm exec prisma migrate dev
```

При необходимости заполнить dev-данные:

```bash
pnpm exec prisma db seed
```

### 5. Запустить проект

Из корня:

```bash
pnpm dev
```

После запуска:

```text
Frontend  http://127.0.0.1:3000
API       http://127.0.0.1:4001/api
Health    http://127.0.0.1:4001/api/health
```

Для настоящей автоматической доставки нужны Yandex Delivery business account и B2B API token.

```dotenv
YANDEX_DELIVERY_ENABLED=true
YANDEX_DELIVERY_TOKEN=
YANDEX_DELIVERY_SOURCE_ADDRESS=
YANDEX_DELIVERY_SOURCE_NAME=
YANDEX_DELIVERY_SOURCE_PHONE=
YANDEX_DELIVERY_SOURCE_EMAIL=

# optional
YANDEX_DELIVERY_SOURCE_LONGITUDE=
YANDEX_DELIVERY_SOURCE_LATITUDE=
YANDEX_DELIVERY_SYNC_INTERVAL_MS=30000
YANDEX_DELIVERY_CALLBACK_URL=https://api.example.com/api/delivery/yandex/callback
```

`YANDEX_DELIVERY_CALLBACK_URL` необязателен. Основная автоматическая синхронизация выполняется backend через `claims/bulk_info`.

Без `YANDEX_DELIVERY_TOKEN` приложение продолжает работать, а сценарий `OTHER` остаётся доступным.

## Auth

Основной пользовательский вход — телефон + одноразовый код.

- OTP TTL: 5 минут;
- повторный запрос: не чаще одного раза в минуту;
- максимум 5 неверных попыток;
- session TTL: 30 дней;
- session token хранится в HttpOnly cookie;
- production cookie использует `__Host-sid`.

В development API возвращает `devCode`, поэтому SMS-провайдер для локальной разработки не требуется.

## Безопасность заказов

- покупатель не получает доступ к заказу только по числовому ID;
- обычные order routes проверяют ownership;
- guest-заказы привязаны к guest session;
- публичный tracking использует криптографически случайный token;
- `/track/:token` не раскрывает полный адрес и другие лишние персональные данные;
- frontend не может произвольно устанавливать `Order.status`, `Delivery.status`, `actualTotal` или финальные суммы.
