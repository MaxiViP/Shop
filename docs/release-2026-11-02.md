## План deployment — только после явного разрешения

Прикладной код кандидата совпадает с production `b676aed`; сам выпуск тестовых
исправлений не требует перезапуска работающего магазина. После зелёного CI
можно сначала согласовать слияние PR и восстановить main без смены runtime.
Если требуется переустановка проверенного SHA, использовать следующий порядок.

1. Зафиксировать полный SHA из одобренного PR и повторно сравнить production
   HEAD, статус, migrations и прикладной diff. При новых серверных изменениях
   остановиться и пересобрать состав релиза. Не устанавливать `origin/main`
   до включения всех 25 production-коммитов.
2. Повторить backup, проверить checksum и архивы. Сохранить исходные units,
   drop-ins, previous SHA и runtime. Не запускать migrate reset, seed/import
   или migrate deploy: новых миграций нет.
3. Собрать отдельный immutable release, оставив прежний runtime нетронутым:

```bash
# Выполнять root только после одобрения; SHA заменить точным проверенным SHA.
set -euo pipefail
SHA='<approved-full-sha>'
[[ "$SHA" =~ ^[0-9a-f]{40}$ ]]

as_shop() { runuser -u shop -- env -i HOME=/home/shop PATH=/usr/local/bin:/usr/bin:/bin COREPACK_ENABLE_DOWNLOAD_PROMPT=0 "$@"; }
cd /opt/korzinamarket
test -z "$(as_shop git status --porcelain)"
test ! -e "$RELEASE"
as_shop git fetch origin release/verified-20261102
test "$(as_shop git rev-parse origin/release/verified-20261102)" = "$SHA"
as_shop git merge-base --is-ancestor b676aed6c5fec97ed0739436bde8014d491e8542 "$SHA"
as_shop git diff --exit-code HEAD "$SHA" -- apps/api/prisma/schema.prisma apps/api/prisma/migrations
as_shop git worktree add --detach "$RELEASE" "$SHA"

as_shop pnpm install --frozen-lockfile
```

4. До переключения проверить фактические upload paths и права shop, scope
   фоновых workers/cleanup timer, доступ к существующим image roots, порядок
   drop-ins и readiness кандидата. Не включать WebP runner/flags и не менять
   Telegram webhook/config. Старые release directories и originals сохраняются.
5. Для атомарной ссылки использовать `/opt/korzinamarket-releases/current`:

   системы. Два новых `zzz-verified-release.conf` должны менять только

## Откат

Новых migrations и прикладных изменений к `b676aed` нет. Для первой установки
через новые overrides достаточно переместить **только созданные этим выпуском**
`zzz-verified-release.conf` в закрытый backup-каталог, выполнить daemon-reload
и перезапустить API/web с прежними сохранёнными overrides. Прежние
`/opt/korzinamarket`, outputs и dependencies не перезаписываются.
Проверить readiness, сайт, uploads и Telegram после возврата.

```bash
# Только после первого switch выше, с тем же проверенным BK.
mv /etc/systemd/system/shop-api.service.d/zzz-verified-release.conf "$BK/api-override.failed"
mv /etc/systemd/system/shop-web.service.d/zzz-verified-release.conf "$BK/web-override.failed"
systemctl daemon-reload
systemctl restart shop-api.service
curl --fail --silent --show-error --retry 10 --retry-connrefused --retry-delay 2 --max-time 10 http://127.0.0.1:4001/api/health/ready
systemctl restart shop-web.service
curl --fail --silent --show-error --max-time 10 -I http://127.0.0.1:3000/
```

Если текущий runtime повреждён, восстанавливать его в отдельный каталог из
проверенного runtime.tgz/source.bundle, затем согласовывать переключение.
Database dump применяется только отдельным явно разрешённым disaster recovery:
откат приложения не означает откат заказов/платежей/БД. Не распаковывать config
поверх действующей конфигурации без сравнения и отдельной проверки.
