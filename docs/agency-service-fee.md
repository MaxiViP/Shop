Статус: структура данных, безопасная миграция, backend и административный frontend.
Новый агентский checkout не включён; требования будущих этапов сохраняются.
Основа: `origin/main`, `508463cfade2112f375dca89d46f2c9e0c9cabdc`, проверен fetch 03.11.2026.
Разработка: `feat/agency-service-fee`, отдельный worktree `F:\Shop\.worktrees\agency-service-fee`.
Ветки делегирования администраторов и унификации телефонов не включены.
Миграция не применялась к рабочей или production-БД. Публичные цены и checkout не переключены.

## 1. Состояние данных и пределы анализа

Read-only проверка доступной локальной БД 03.11.2026 выполнена с
`default_transaction_read_only=on`, `BEGIN READ ONLY` и ограничением времени запроса.
Получены только агрегаты, без выгрузки пользователей, заказов и секретов:

- 173 товара, у всех `serviceMarkupPercent = 10`;
- значений NULL или вне 0–100: 0;
- событий `AdminAudit.action = PRODUCT_MARKUP_CHANGED`, `entity = PRODUCT`: 0;
- в шести версионируемых JSON-файлах `apps/api/data` найдено 458 вхождений
  `serviceMarkupPercent`, единственное значение 10, нарушений диапазона нет.
  Это отчёты, а не 458 независимых товаров.

Эти результаты не описывают production. Повторяемый read-only запрос находится в
`apps/api/prisma/check-service-fee.sql`; запускать только на явно выбранной разрешённой локальной БД.
Миграция независимо повторяет проверку диапазона под блокировками, чтобы результат
предварительной проверки не мог устареть между чтением и переносом.

Происхождение 10% нельзя достоверно восстановить: миграция
`20261018120000_point_owners` добавила default 10, форма создания также отправляет 10,
создание не журналирует отдельный выбор процента, а повторное сохранение 10 → 10
не порождает `PRODUCT_MARKUP_CHANGED`.
Ссылки: `apps/api/src/admin/products.service.ts:create/update`,
`apps/web/app/components/admin/ProductForm.vue`, `apps/api/src/product/pricing.ts`.
Отсутствие события не доказывает автоматическое происхождение.
Даже отдельное событие смены процента не является полным журналом всех старых путей записи.

## 2. Поля и безопасный перенос

- `ShopSettings.globalServiceMarkupPercent Int @default(10)` + SQL CHECK 0–100.
- `Product.serviceMarkupPercentOverride Int?` + SQL CHECK NULL либо 0–100.
- `Product.serviceMarkupNeedsReview Boolean @default(false)`.
- `Product.serviceMarkupPercent Int @default(10)` остаётся существующим эффективным значением.
- `normalizedPrice`, его generated expression, индекс, денежные формулы и округление не меняются.

Миграция `20261103150000_global_service_fee` одной транзакцией:

1. Ограничивает ожидание блокировки 5 секундами и блокирует ShopSettings, затем Product.
2. При NULL/проценте вне диапазона останавливается с ошибкой до DDL; ничего не исправляет автоматически.
3. Добавляет поля и ограничения.
4. Копирует существующий процент каждого товара в override без изменения исходного поля и цены.
5. Консервативно ставит review всем существующим 10%. Это метка неопределённости,
   а не утверждение, что процент был default. Даже намеренные 10% сохраняются как override.
   Ложноположительная необходимость проверки безопаснее потери индивидуальной настройки.
6. Не меняет updatedAt товара, заказы, snapshots, платежи, промокоды, доставку и аудит.

Никакого массового NULL, пересчёта цен или автоматической классификации по отсутствию аудита нет.
Вновь вставленные строки имеют override NULL и review false.

В ЭТАПЕ 1.1 политика `override ?? globalServiceMarkupPercent` ещё НЕ активна:
старый код продолжает читать/писать существующий эффективный процент и использовать прежний default 10.
Изменение глобального поля SQL-запросом само по себе не меняет цены.
Нет API/UI для новой настройки и нет синхронизирующего триггера.
В частности, новая строка при глобальном значении 25 пока всё ещё получит эффективные 10;
это намеренная совместимость подготовительного этапа, не готовность к переключению.

До ЭТАПА 1.2 миграцию не выкатывать в production без отдельного разрешения.
Если foundation будет отдельно применена в иной разрешённой среде со старым приложением,
старый admin PATCH может изменить только эффективное поле и оставить старый override.
Поэтому перед активацией политики обязательны повторная сверка расхождений,
обновление ВСЕХ writers и согласованное переключение. CHECK равенства override/effective
сейчас не вводится: он сломал бы действующий код.

Проверки исторических данных сравнивают все строки всех остальных таблиц, включая
непустые фикстуры обычного и гостевого заказов, nullable/заданный snapshot,
PAID-платёж, доставку, промокод, услугу, изменение цены и отмену.
Для Product сравниваются все старые колонки, включая timestamp и normalizedPrice;
отдельно сравниваются определение generated column, номер колонки, индекс и порядок сортировки.

## 3. Будущий массовый переход в глобальный режим — только проект

Сейчас endpoint, UI и выполняющая команда НЕ реализуются.

Будущий процесс имеет два отдельных действия уполномоченного администратора:

1. Предпросмотр выбранного набора товаров. Показать ID, режим, старый override,
   review, эффективный процент, текущую цену продавца, глобальный процент,
   новые эффективный процент и цену, разницу и число товаров.
   Особо выделять 0%, намеренные исключения и неоднозначные 10%.
   Никаких изменений при preview.
2. Явное подтверждение конкретного предпросмотра. Перед записью проверить серверный
   fingerprint/version набора, глобального процента и исходных значений товаров.
   Изменение любой значимой предпосылки требует нового preview.

Подтверждённая операция атомарно очищает override, снимает review, устанавливает
эффективное значение по актуальному глобальному проценту и создаёт аудит.
Нужны UUID операции, защита от повторов с другим содержимым, актор, причина,
точный состав, старые/новые режимы и проценты, связь с предпросмотром.
0 не трактуется как NULL. Товары вне подтверждённого набора не изменяются.
Глобальная смена и массовый переход — разные операции.
Для больших наборов сначала измерить время блокировок; нельзя незаметно разбивать
подтверждённую атомарную операцию на частично применяемые пакеты.

## 4. Порядок блокировок и стратегия будущих транзакций

Проверенные текущие пути:

| Путь | Текущий порядок |
| --- | --- |
| `OrderService.save` | advisory checkoutRequestId → Product по ID FOR SHARE → Category FOR SHARE → ShopSettings FOR UPDATE |
| `CartService.checkoutResultIn` | User FOR UPDATE → Cart FOR UPDATE → Product FOR SHARE → `OrderService.save` |
| `SettingsService.update` | ShopSettings FOR UPDATE; сейчас не обновляет товары |
| `OrderService.schedule`, `StaffService.restore` | ShopSettings FOR UPDATE → Order FOR UPDATE |
| `StaffService.item/itemPrice/finishAssembly/confirmPayment` | Order FOR UPDATE; работают со снимками заказа |
| `CoordinationService.decide/propose` | Order FOR UPDATE → Product → Category; цены используют процент заказа |
| `recordStaffAudit` | после доменной операции читает User FOR SHARE |

Файлы: `apps/api/src/order/order.service.ts`, `apps/api/src/cart/cart.service.ts`,
`apps/api/src/admin/settings.service.ts`, `apps/api/src/admin/products.service.ts`,
`apps/api/src/staff/staff.service.ts`, `apps/api/src/staff/audit.ts`,
`apps/api/src/order/coordination.service.ts`.

Опасный цикл при наивном добавлении глобального пересчёта:
checkout держит Product и ждёт ShopSettings; администратор держит ShopSettings и ждёт Product.
Serializable сам по себе не устраняет такой цикл.

Стратегия ЭТАПА 1.2 для операций, использующих текущую политику каталога:

- Разрешить/проверить identity и гостевой доступ до доменных блокировок.
- Внешние блокировки User/Cart и идемпотентности, когда они нужны, получать до ShopSettings.
  Операции настроек не должны затем захватывать Cart или заказы покупателей.
  Нужные блокировки пользователя-актора для проверки полномочий получать заранее,
  учитывая FK аудита и параллельное изменение ролей.
- Единый порядок общих доменных ресурсов:
  **ShopSettings → Order (если нужен существующий заказ) → Product по возрастанию ID → Category по ID → дочерние строки**.
- Checkout сохраняет необходимый ShopSettings FOR UPDATE для очереди, но получает его
  ДО первого Product lock, включая внешний lock в CartService. Простая перестановка
  только внутри OrderService недостаточна.
- Глобальный пересчёт: ShopSettings FOR UPDATE → затронутые Product по ID FOR UPDATE;
  только override IS NULL, аудит в той же транзакции; без блокировок исторических заказов.
- Создание/смена override и все import/seed writers должны координироваться с тем же
  mutex ShopSettings до Product. Для читателей политики возможен FOR SHARE,
  если в этой транзакции не потребуется последующее повышение до FOR UPDATE.
  Нельзя начинать с FOR SHARE и повышать блокировку при конкурентных checkout.
- Читать глобальный процент, цены для quote и проценты для snapshot в одной согласованной
  транзакции. Проверить и повторные чтения внутри CartService.snapshot.
- Существующие операции сборки/оплаты используют снимки и НЕ начинают читать живую
  настройку под уже захваченным Order. Если операция действительно потребует обеих
  сущностей, перенести получение ShopSettings на её внешнюю границу до Order.
- Учесть текущий Order → User в аудите и Order → TelegramIdentity в reserveReply;
  порядок внешних identity/user locks нельзя менять локально без анализа всех вызывающих путей.
  Не объявлять весь существующий workflow свободным от deadlock по одной перестановке.
- Короткие транзакции, ограниченные lock/statement timeout; внешние HTTP и отправка
  уведомлений только после commit/outbox. Ограниченный retry всей транзакции при
  PostgreSQL 40P01/40001 или Prisma P2034 разрешать лишь с той же идемпотентностью,
  без повторных платежей и внешних side effects.

До включения глобального пересчёта обязательны конкурентные тесты: global update ×
guest checkout × cart checkout × Telegram checkout × product create/override,
а также schedule/restore и отзыв полномочий. Проверять отсутствие зависания,
согласованность цены/snapshot и атомарный аудит, а не только успешный HTTP.
В ЭТАПЕ 1.1 checkout, платежи и порядок runtime-блокировок не меняются.

## 5. Требования будущей агентской модели и юридической инфраструктуры

Это технические требования для последующего согласования, не юридический текст оферты.
Содержание документов и достаточность формулировок согласуются отдельно.

### Публичные страницы и публикация

- Переработать `/how-it-works` с посылом:
  «Ваш человек на рынке. Вы выбираете — мы покупаем и доставляем».
- Создать отдельную `/legal/agency-offer`.
- Хранить документ и неизменяемые опубликованные версии: ID документа, ID/номер редакции,
  дату публикации, дату начала действия, полный текст и его digest.
  Опубликованный текст нельзя редактировать/заменять на месте; исправление — новая редакция.
  Старые редакции остаются доступны для доказательства акцепта.
- Зафиксировать однозначное правило выбора действующей опубликованной версии по времени;
  будущая дата действия не делает документ доступным для акцепта раньше срока.

### Акцепт при первоначальном оформлении

- Акцепт действием кнопки «Оформить заказ», без обязательного чекбокса оферты.
  Рядом с действием показать понятное уведомление об акцепте и ссылку на конкретную редакцию.
- Сохранить документ ID, version ID/номер, серверную дату/время акцепта, order ID,
  user ID либо guest session ID, канал оформления (WEB/TELEGRAM), идентификатор попытки.
  Guest session ID — внутренняя связь, не значение cookie/токен.
- Неизменяемая связь акцепта с полным текстом конкретной опубликованной редакции,
  её digest и уведомлением/действием оформления; одной ссылки на «текущую оферту» недостаточно.
- Сохранять акцепт и новый заказ атомарно. Повтор оформления возвращает тот же результат,
  не создаёт новый акцепт и не привязывает старую попытку к другой редакции.
- Передавать ожидаемую редакцию/контекст предпросмотра; сервер повторно проверяет её
  публикацию и актуальность внутри транзакции. Устаревшая версия требует показать
  новую редакцию и повторить явное действие; нельзя молча принять новую за клиента.
- Покрыть сайт, гостя и Telegram-бот. Для Telegram сохранить тот же смысл уведомления,
  ссылку на редакцию и связь callback/подтверждения с показанной версией.

### Окончательная смета и платёж

- Первоначальный акцепт оферты и согласие на окончательную сумму — разные события.
- Окончательную смету отдельно подтверждают кнопкой «Подтвердить и оплатить».
- Смета имеет неизменяемую версию с составом, количеством, ценами продавцов,
  вознаграждением, скидками, доставкой и общей суммой в копейках.
- Сохранять, кто, когда и в каком канале подтвердил именно эту версию.
  Любое значимое изменение аннулирует возможность оплаты прежней версии и требует
  нового согласования. Платёж идемпотентно связан с подтверждённой версией сметы.
- Последующие фактические расходы, возврат и отчёт о закупке — отдельные записи;
  нельзя переписывать принятую смету или старые снимки.

### Согласия и безопасное включение

- Обработка согласий на персональные данные и рекламные рассылки раздельная:
  независимые основания/события и версии документов; реклама не включается автоматически
  фактом заказа или акцепта оферты. Конкретные требования согласуются юридически.
- Предусмотреть серверный feature flag `AGENCY_CHECKOUT_ENABLED`, по умолчанию **false**.
  В ЭТАПЕ 1.1 это требование к будущей реализации; flag и новые checkout routes не добавляются.
- Пока flag выключен, существующий production-checkout работает как раньше и
  НЕ зависит от наличия агентской оферты. Клиент не может сам включить модель.
- При включённой новой модели отсутствие обязательной действующей опубликованной
  оферты блокирует её оформление, без создания заказа/платежа/ложного акцепта и без
  скрытого отката на старую модель.
- Сохранить версию модели на заказе: переключение flag не меняет workflow уже созданных заказов.
- **Инфраструктура версий оферты и фиксация акцепта должны быть реализованы и
  протестированы ДО запуска нового оформления и оплаты.**
  Включение новой модели в production требует отдельного разрешения после юридического
  согласования документов и приёмки WEB/guest/Telegram-сценариев.

Оферта сейчас не написана и не опубликована; публичные страницы не изменены.

## 8. Backend ЭТАПА 1.2

Этот раздел описывает реализованный backend и заменяет предложенную в разделе 4
стратегию перестановки блокировок checkout. Разделы об ЭТАПЕ 1.1 выше — история
подготовки, а не описание включения новой агентской модели.
Миграция `6ea1c0c` проверена до изменений: критических ошибок переноса не обнаружено.
Новых миграций и изменений Prisma-схемы в ЭТАПЕ 1.2 нет.

### Контракты

- `GET /admin/settings` возвращает `globalServiceMarkupPercent`.
- `PATCH /admin/settings` принимает целое 0–100. Изменение доступно только
  уполномоченному администратору существующей модели доступа. Роль и основной телефон
  повторно проверяются внутри транзакции под блокировкой записи администратора.
- `POST /admin/products`, `PATCH /admin/products/:id` и
  `POST /admin/products/pricing` принимают `serviceMarkupPercentOverride`: NULL — глобальный
  режим, целое 0–100 — индивидуальный. Отсутствие поля при создании означает NULL,
  при PATCH — сохранить прежний режим.
- Передача производного `serviceMarkupPercent` либо `serviceMarkupNeedsReview` в mutation
  или preview отклоняется строгой схемой. В ответах эффективный процент остаётся.
- Owner API не принимает процент/режим; создание наследует глобальный, обычный PATCH
  сохраняет индивидуальное исключение. Preview владельца использует режим его товара.
- Формула `effectivePercent(override, globalPercent)` централизована в
  `apps/api/src/product/pricing.ts`. Индивидуальный 0 не заменяется глобальным значением.
- Цена продавца сохраняется отдельно; `customerPrice` и денежное округление прежние.
  Снимки старых заказов, исправление цены позиции и fallback 10 не изменены.

Переключение режима явно снимает review и журналируется, даже если эффективные 10%
остаются 10%. Обычное редактирование review не снимает. Для глобальной смены есть
`GLOBAL_MARKUP_CHANGED`, для затронутых товаров — `PRODUCT_MARKUP_CHANGED` со старым
и новым состоянием; создание товара через административный/owner сервис фиксирует
`PRODUCT_MARKUP_CREATED`. Сохранение, пересчёт и аудит атомарны.

Все старые override остаются исключениями. Массового перевода 173 товаров в глобальный
режим нет. Обнаруженное расхождение заданного override (включая 0%) и эффективного поля блокирует
глобальное изменение с 409; обычный PATCH такого товара также требует явного решения
о проценте. Backend не угадывает намерение старого приложения.

### Конкурентность без изменения checkout

Перестановка блокировок в checkout не понадобилась. Глобальная операция выполняет:

1. User администратора `FOR SHARE NOWAIT`.
2. `LOCK TABLE Product IN EXCLUSIVE MODE NOWAIT`.
3. ShopSettings `FOR UPDATE NOWAIT`.
4. Проверку расхождений, изменение настройки, эффективных процентов глобальных товаров
   и аудит одной транзакцией.

EXCLUSIVE конфликтует с Product ROW SHARE, который PostgreSQL получает при checkout
`FOR SHARE`, и с ROW EXCLUSIVE записей товаров. Обычный SELECT каталога совместим.
Операция никогда не ждёт ни Product, ни ShopSettings: SQLSTATE 55P03 преобразуется из
обёртки Prisma driver adapter в HTTP 409. Транзакция полностью откатывается.
Нельзя заменить NOWAIT ожиданием только на одной из этих блокировок: вновь появляется
цикл Product → ShopSettings либо цепочка через ShopSettings → Order → Product.
Автоматического повтора глобальной операции нет: администратор обновляет данные и
осознанно повторяет действие. Поддерживаются также стандартные конфликты 40001/40P01.

Обычные price writers получают `Product ROW EXCLUSIVE` через `lockMarkup` до первого
чтения в транзакции, в том числе до фиксации Serializable snapshot. После этого глобальный
процент не изменится до commit. Это важно для новых товаров, у которых ещё нет строки,
и для ожидания завершения глобального пересчёта. Настройку они читают без повышения
до FOR UPDATE. Изменение существующего товара дополнительно блокирует его строку.

Цена и snapshot checkout продолжают читаться из одного сохранённого эффективного поля
под прежними блокировками Product. Глобальная публикация не может попасть между ними.
Модули order/cart, Telegram checkout и платежи не изменены.

Ограничение: редкое глобальное изменение может вернуть 409 при активной сборке,
checkout, обновлении рейтинга или записи каталога. Это сознательный безопасный отказ,
а не частично применённый процент. На большом каталоге нужно отдельно измерять время
пересчёта и объём per-product аудита; нельзя снимать блокировку или разбивать атомарную
операцию на незаметные пакеты.

### Проверенные пути Product

- `AdminProductsService` и Owner API: создание/редактирование синхронизируют режим,
  эффективный процент и review; независимая запись производного поля запрещена.
- `data/market-products/import.ts`: apply фиксирует политику до чтения; новые товары
  глобальные, существующие override сохраняются, preview учитывает актуальный процент.
- `data/catalog-import/import.ts`: новые черновики наследуют текущий глобальный процент;
  обновление деталей не изменяет индивидуальный режим. Preview использует тот же процент.
- `prisma/seed.ts`: актуальная политика и сохранение override. Категории обновляются до
  транзакции товаров; существующие seed-товары блокируются по ID до записи, чтобы не
  пересекаться обратным порядком с Product → Category checkout.
- `data/sale-audit/apply.ts`, hits/seasons, photo/image operations: эти пути не меняют
  поля процента или режим. Их обычные блокировки записи/строк Product уже конфликтуют
  с глобальной EXCLUSIVE; изменения их предметной логики не требуются.

Прямой SQL, ручной PrismaClient и сторонний скрипт, обходящие эти пути и `lockMarkup`,
не являются поддерживаемым интерфейсом изменения процентов. Синхронизирующего триггера
нет; привилегированным SQL можно нарушить инвариант, поэтому предусмотрено обнаружение
legacy drift и проверка диапазонов существующими SQL CHECK.

### Права и ограничения

В этой ветке `AdminGuard` требует одновременно ADMIN и настроенный главный телефон.
`AuthService.me()` не возвращает сессию постороннего ADMIN; имеющийся frontend
middleware ADMIN использует этот ответ. Owner/SELLER не получают новые полномочия.
Новая модель делегирования сюда не включена. Frontend требует контрактов backend 1.2
и foundation-миграции 1.1; их выпуск и применение к целевой БД требуют отдельного
разрешения и на этом этапе не выполняются. При её интеграции отдельно согласовать
capability управления процентами с backend, не ограничиваться скрытием кнопок.

Не добавлены псевдофильтр текущей страницы и массовые клиентские PATCH:
серверного фильтра режима/review и транзакционного bulk preview/apply пока нет.

173 существующих товара автоматически не переводятся на общий режим.

### Bulk API и выборка

- `POST /admin/products/service-fee/bulk/preview` принимает
  `{ selection, mode: "global" }`. Selection — `{ kind: "ids", ids: [...] }`
  или `{ kind: "filter", filter: {...} }`. Лимит — 1000 уникальных товаров;
  пустой выбор, отсутствующие ID и превышение лимита отклоняются.
- Preview возвращает подписанный `previewToken`, срок действия, общий процент,
  количество выбранных/изменяемых товаров, серверные цены продавца/покупателя,
  прежний override/review, будущий режим, разницу в копейках и базисных пунктах.
  Итоги — сумма цен за указанные единицы товаров, а не сумма заказа.
  Preview выполняется в READ ONLY / REPEATABLE READ и ничего не записывает.
- `POST /admin/products/service-fee/bulk/apply` принимает только
  `{ previewToken, requestId: UUID, confirmed: true }`. Цены клиента не принимаются.
  Результат содержит requestId, count, changedCount, skippedCount, globalPercent,
  appliedAt и productIds. Оба POST возвращают HTTP 201 при успехе.
- `GET /admin/products` поддерживает `serviceFeeMode=global|individual|review`
  и фильтр эффективного `serviceMarkupPercent`, включая 0. Фильтры поиска,
  категории, точки, активности и остальных прежних полей общие для списка,
  count и bulk. Фильтрация выполняется до пагинации; list/count читаются
  из одного REPEATABLE READ snapshot. Filter selection охватывает весь результат.

В UI отдельный выбор процентов сохраняется между страницами и не смешивается
с выбором ХИТ. Можно выбрать отмеченные товары, все review, все индивидуальные
(включая подтверждённый 0%) или весь применённый фильтр. Preview имеет пагинацию
по 20 строк и обязательное явное подтверждение. По умолчанию ничего не выбрано.
Ни открытие списка, ни preview, ни миграция не переводят старые 173 товара.

### Устаревший preview и атомарность

HMAC-SHA256 связывает токен с ADMIN, выбранным набором, режимом, nonce,
сроком действия 10 минут и SHA256 fingerprint. Fingerprint включает настройку
и её updatedAt, выбранные ID, имена, исходные цены, единицы/priceQty,
режим, review и updatedAt товаров. При apply сервер повторяет ту же выборку
и расчёт под блокировками. Изменение состава фильтра, товара или настройки
(даже изменение и возврат прежнего процента) требует нового подтверждения.
Устаревший preview возвращает HTTP 409 / SERVICE_FEE_STALE без записи.

Порядок apply: User FOR SHARE NOWAIT, advisory lock requestId без ожидания,
проверка сохранённого результата, Product EXCLUSIVE NOWAIT, ShopSettings
FOR UPDATE NOWAIT, проверка fingerprint, обновление, AdminAudit и durable result.
Циклы ожидания с прежним checkout не добавляются. Занятые блокировки дают 409.
Ошибка товара, аудита или сохранения результата откатывает всю операцию.
Цена продавца сохраняется; эффективный процент, nullable override и review
обновляются вместе; PostgreSQL пересчитывает прежний generated normalizedPrice.
На каждый изменённый товар создаётся один PRODUCT_MARKUP_CHANGED со старым/новым
состоянием, ценами, единицами и requestId. Уже глобальные неизменённые строки
пропускаются без изменения updatedAt и без повторного аудита.

### Потеря ответа после commit

Аддитивная миграция `20261104090000_service_fee_bulk_operation` создаёт только
ServiceFeeBulkOperation; Product, настройки, заказы и generated expression не меняются.
UUID requestId — PK; запись связывает ADMIN, hash исходного токена и JSON результата.
Она фиксируется в одной транзакции с товарами и AdminAudit. Промежуточных записей
о незавершённых операциях в таблице нет.

При сетевой ошибке UI сохраняет requestId и токен. Повтор идентичного запроса
возвращает сохранённый результат ДО проверки срока токена и текущих цен:
повторной записи товаров/аудита нет даже после смены настройки или ключа подписи.
Другой токен с тем же requestId даёт 409; другой ADMIN не получает результат.
Одновременный запрос с тем же UUID получает SERVICE_FEE_IN_PROGRESS / 409
или уже зафиксированный результат. После IN_PROGRESS разрешён явный повтор
с прежним UUID. После stale нужно получить и подтвердить новый preview.
Сохранённые результаты нельзя очищать без отдельного решения о сроке идемпотентности.

### Конфигурация и воспроизведение

В production требуется отдельный секрет SERVICE_FEE_PREVIEW_SECRET длиной не менее
32 байт, одинаковый у всех API-процессов и сохраняемый между перезапусками.
Его значение хранится только в secrets окружения. Без него preview/apply нового
запроса закрыты с 503. Уже сохранённый результат можно повторно получить без
проверки подписи прежним ADMIN. В development/test используется случайный ключ
процесса; перезапуск требует нового preview, но не отменяет committed requestId.

Новая миграция применяется обычным migrate deploy при отдельно разрешённом
развёртывании. На этом этапе production не изменялся; feature flags агентского
checkout не включались, юридическая инфраструктура и ЭТАП 2 не начинались.

Профильные интеграции из apps/api (только SERVICE_FEE_TEST_DATABASE_URL
с отдельной локальной БД service_fee_test_<32 hex>, без fallback на DATABASE_URL):
