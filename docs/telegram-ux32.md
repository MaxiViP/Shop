# Telegram UX 3.2

CUSTOMER screens share left-aligned native Rich button rows. Paragraphs and HTML fallback emphasize money and order numbers. RichMessageButton labels officially permit plain text/custom emoji/date entities only, so bold text is not placed inside buttons. STAFF rendering and commands remain unchanged. API references: [buttons](https://core.telegram.org/bots/api#richmessagebutton), [alignment](https://core.telegram.org/bots/api#inputrichblockbuttons).

History displays each owned order once, as a button with its number, status icon, final or explicitly preliminary/unknown sum, Moscow creation time and question/unread counters. It keeps existing callbacks and pagination. Quick products display current server unit prices on selection buttons without a repeated text list; direct product/page context and revision-guarded repeat-order behavior remain.

The home menu groups catalog/cart, quick purchases/orders, receiving, contact/help. Questions/unread updates precede an active order and duplicate priority actions for the same order are suppressed. Contact opens owned order selection; conversations retain their existing order binding.

Receiving reuses the existing CHECKOUT session with a `purpose: RECEIVING` payload marker and logical `stage`. Physical states remain compatible with the existing database check constraint; no schema/migration is needed. Ordinary checkout choose/reply/confirm explicitly reject this marker. No cart revision, quote token or financial values are invented. Existing address-field validation/prompts are shared.

Customers can choose pickup/delivery, inspect owned addresses, select a default address, or add/edit one through bound replies and explicit review/save. Selection/save checks the current session nonce, ownership, expiry and saved address timestamp. New addresses and edits are durable in the existing profile. Method preferences last 30 minutes after confirmation, survive ordinary menu/cart/catalog navigation, and are consumed by normal checkout. Other input flows can replace the single session; /cancel clears the preference. Existing orders are never changed, and only the original explicit checkout confirmation can create an order. Checkout rechecks prices, availability, minimums and receiving rules.

`customer-commands.ts` is the source for eight CUSTOMER commands. Export its compiled array with the current Rich CUSTOMER chat allowlist to a private manifest. Run `scripts/telegram-customer-commands.mjs <manifest> <backup> apply` on the gateway using its existing environment. It backs up current chat-scoped commands for default/Russian language, applies and verifies each scope without retries. `verify` checks the result; `restore` restores the matching bot/scope backup. It does not change default/global commands, STAFF, webhook, gateway code or transport allowlists. This test release exposes the command menu only to the existing CUSTOMER test allowlist. [setMyCommands](https://core.telegram.org/bots/api#setmycommands).

Visual acceptance: Desktop/Android menu density and left alignment; history labels/date/status/sums, questions and pagination; current prices and repeat navigation in quick purchases; receiving/address review and explicit save; normal checkout after choosing pickup/delivery; existing 2-column 4:3 gallery and bottom cart total. Real client visual acceptance remains a user check.
