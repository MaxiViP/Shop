# Глобальное включение Telegram Rich

`rich-policy.ts` читает конфигурационный файл на каждом показе экрана. Кеширования policy и необходимости перезапуска нет. Без `global` сохраняется прежний allowlist. Для включения всех приватных чатов соответствующих ботов:

```json
{"enabled":true,"global":{"customer":true,"staff":true}}
```

Можно сохранить прежние массивы `customer`/`staff`: они продолжают разрешать Rich, если глобальный флаг конкретного бота выключен. Неизвестные поля, неверные типы, недоступный/повреждённый/слишком большой файл отключают Rich. Группы и некорректные chat ID остаются вне Rich-режима.

Это флаг **представления**, не авторизации. CUSTOMER продолжает проверять принадлежность корзин/заказов, контакт и checkout. STAFF сохраняет приватный чат, существующий список допущенных администратором Telegram-аккаунтов, привязку, актуальную роль/права, версии и подтверждения действий. Глобальный Rich не даёт доступа к данным или операциям. Дизайн, финансовые правила, Mini App и gateway не изменяются. Обычные контактные клавиатуры, ForceReply и фоновые уведомления сохраняют прежний транспорт.

## Экстренное отключение

На основном VPS `root@2.59.40.12` выполнить:

```bash
install -o root -g shop -m 640 /dev/null /etc/korzinamarket/telegram-rich.json.next
printf '%s\n' '{"enabled":false}' > /etc/korzinamarket/telegram-rich.json.next
mv -f /etc/korzinamarket/telegram-rich.json.next /etc/korzinamarket/telegram-rich.json
```

Следующий send/edit использует экранированный HTML и те же inline callback. Уже показанные сообщения изменятся при следующем действии пользователя; исторические сообщения не переписываются массово. Не нужны deploy, restart, смена webhook или восстановление БД. Чтобы вернуть только тестовый режим, атомарно восстановить исходную конфигурацию из backup. Для повторного глобального включения атомарно записать JSON выше с теми же owner/group/mode.

## Выпуск и проверка

Сначала развернуть проверенный API с прежней policy. Сохранить полный backup БД/uploads/runtime/config, проверить архивы и восстановление дампа исключительно в отдельную тестовую БД. Затем атомарно включить оба глобальных флага, сохранив исходные allowlist и отдельную копию policy для отката. Контролировать health, gateway/tunnel/webhook и ошибки; сначала отключать Rich, если проблема относится к представлению. При откате кода восстановить также исходную policy, поскольку прежний строгий парсер не знает поля `global`. Данные заказов при UI-откате не восстанавливаются.

Автоматические проверки охватывают независимость ботов, старые списки, переходы global/off/allowlist, send/edit/HTML fallback, JPEG upload, подтверждённые отказы и неизвестный результат без повторной отправки. Изолированные PostgreSQL E2E проверяют полный CUSTOMER каталог/корзину/checkout/защиту повторного подтверждения и STAFF очереди/вес/отказ после отзыва роли при глобальной policy.

Реальную доставку вне прежних списков следует подтверждать отдельными существующими тестовыми аккаунтами с действующим доступом. Нельзя считать удаление прежнего тестового ID из массива или синтетический ID проверкой нового аккаунта; нельзя расширять STAFF-права ради smoke. Недоступность такого аккаунта фиксируется отдельно от результатов автоматических тестов и выпуска.
