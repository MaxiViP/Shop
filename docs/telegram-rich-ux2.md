# Telegram Chat UX 2.0

## Реализация

Визуальная система использует реальные схемы Bot API 10.3: `sendRichMessage`, `InputRichMessage.blocks`, `editMessageText.rich_message`, heading, paragraph, divider, table, details, photo и buttons. Основание: [Bot API](https://core.telegram.org/bots/api), [changelog](https://core.telegram.org/bots/api-changelog), [features](https://core.telegram.org/bots/features). Произвольного CSS нет.

`rich.ts` описывает типизированное представление и проверяет ограничения. `rich-policy.ts` читает внешнюю конфигурацию перед каждым экраном. `delivery.ts` выбирает Rich или экранированный HTML с inline-клавиатурой. `bot-api.ts` различает подтверждённый отказ, неизменённое сообщение, невозможность редактирования и неизвестный исход. Gateway разрешает новый метод, сохраняя ограничения размера и один сетевой запрос.

Rich применяется к интерактивным экранам покупателя и сотрудника: меню, каталог, карточки товаров, корзина, быстрые покупки, заказы, вопросы, оплата, рабочий обзор, сборка и подтверждения. Запросы контакта, ForceReply и фоновые уведомления остаются обычными сообщениями. Фото и подписи в переписке заказа используют существующий безопасный просмотр на сайте. Mini App не изменён.

Категории выводятся по две кнопки в строке, с count доступных категорий и страницами по восемь. Списки товаров показывают диапазон и общее количество. Категория/страница сохраняются в callback товара; возврат из корзины и быстрых покупок также сохраняет источник. История, вопросы и очереди продавца показывают номер страницы и количество страниц. Поток сообщений сохраняет существующие курсоры и приоритет непрочитанного.

## Количество и безопасность

Прежний callback карточки содержал черновое выбранное количество; после добавления карточка снова строилась от минимального значения. Новый экран показывает фактически сохранённую корзину. Кнопки передают дельту, единицу, ревизию и контекст, без отдельного черновика или «Добавить выбранное».

`adjust` читает текущую корзину, проверяет ревизию и передаёт `set`/`remove` существующему CartService. CartService остаётся источником правил, блокировок, денежных расчётов, шага и авторизации. После записи используется возвращённый серверный snapshot. Цена действия рассчитывается существующей серверной моделью в копейках; вес остаётся в граммах. Целые экземпляры выбираются только в штуках/пучках и взвешиваются прежним механизмом.

Обработка чата сериализуется до завершения показа экрана. Повторный `update_id` подавляется ограниченным краткоживущим кешем; долговременную и межпроцессную защиту обеспечивают ревизии корзины, версии вопросов и существующие durable claims. Старое действие перечитывает корзину и не создаёт подтверждения добавления. После потерянного ответа записи выполняется чтение, без повторной мутации.

Fallback разрешён только после подтверждённого отказа Telegram 400/404. Отказ загрузить фото позволяет один раз показать Rich без фото. Таймаут, потерянный/некорректный ответ и 5xx не порождают повторную отправку. 429 и 403 также не приводят к немедленному fallback. При достоверно удалённом/нередактируемом сообщении отправляется замена и сохраняется новый message ID; staff flow привязывает его через CAS. Подтверждение финансовых действий требует прежней проверки версии и прав.

Строки пользователей передаются как буквальный RichText, без интерпретации разметки; HTML fallback экранируется. Фото разрешены только по HTTPS с origin магазина и путями изображений. Основные операции количества не загружают фото: оно запрашивается при открытии подробностей.

## Feature flag

В `api.env` задаётся только путь `TELEGRAM_RICH_CONFIG_FILE=/etc/korzinamarket/telegram-rich.json`. Сам JSON хранится вне репозитория, root:shop, 0640:

```json
{"enabled":true,"customer":["TEST_CHAT_ID"],"staff":["TEST_CHAT_ID"]}
```

В режиме allowlist используются цифровые строки существующих чатов. Глобальный режим задаётся независимо для каждого бота и не требует перечисления ID:

```json
{"enabled":true,"global":{"customer":true,"staff":true}}
```

Существующие `customer`/`staff` списки можно сохранить рядом с `global`. Для каждого бота Rich разрешён его глобальным флагом **или** его списком. Отсутствующий/ложный глобальный флаг сохраняет прежний режим allowlist. `enabled:false` имеет приоритет над обоими способами включения. Глобальный режим меняет только представление: приватный чат, привязка сотрудника, существующие роли и `TELEGRAM_ADMIN_CHAT_IDS` проверяются как прежде. Отсутствующая/невалидная конфигурация отключает Rich. Файл следует заменять атомарно, не редактировать частично. Подробности — [глобальный rollout](telegram-rich-global.md).

Быстрое отключение на основном VPS без перезапуска приложения:

```bash
umask 027
printf '%s\n' '{"enabled":false}' > /etc/korzinamarket/telegram-rich.json.next
chown root:shop /etc/korzinamarket/telegram-rich.json.next
chmod 640 /etc/korzinamarket/telegram-rich.json.next
mv /etc/korzinamarket/telegram-rich.json.next /etc/korzinamarket/telegram-rich.json
```

Это меняет представление следующих экранов и не меняет заказы/корзины. Уже отправленные сообщения остаются в истории; новые действия обновят их через обычный режим.

## Ручная приёмка в настоящем Telegram

Повторить на Telegram Desktop Windows и Android Samsung Galaxy S25 Ultra, после обновления клиента при необходимости:

1. Покупатель: `/start`, проверить Rich-меню и заметность ожидающего вопроса.
2. Каталог: две колонки, длинные названия, страницы, отсутствие пустой последней страницы.
3. Зелень → укроп. При исходном нуле: `+1` → 1, `+2` → 3, `−1` → 2, `+2` → 4. Суммы должны соответствовать текущей серверной цене.
4. Корзина → укроп: остаётся 4; «К товарам» возвращает на исходную страницу. Изменение из корзины сохраняет её страницу.
5. Весовой товар: только разрешённый шаг, предварительная стоимость. Целый экземпляр: только целые штуки/пучки; ожидаемый вес или «После взвешивания».
6. «Фото и описание»: фото, подробности; проверить работу без фото. Сравнить скорость обычных кнопок количества.
7. Двойное нажатие/старая карточка: нет двойного добавления; показано актуальное количество. Потеря связи: перечитать `/cart`, не повторять неизвестный платёж/оформление.
8. Заказ: статус, прогресс, товары/доставка/услуги, предварительная или итоговая сумма. Согласование: версия, разница веса/цены и безопасный ответ.
9. Переписка: непрочитанное, ответ на приглашение, возврат к заказу. Из продавца `/work`: «Нужно вам», «Ждём покупателя», сборка, вес, исправление, возврат и подтверждение.
10. Проверить нативные цвета primary/success/danger, переносы, таблицы, сворачивание подробностей и редактирование того же сообщения. Отключением flag проверить обычные сообщения и кнопки, затем восстановить allowlist.

Не подтверждать реальные денежные поступления и не уведомлять внешних клиентов ради проверки. Реальная визуальная приёмка Android/Desktop остаётся отдельным этапом после подтверждённой доставки Rich.

## Выпуск и восстановление

Только основной VPS `/opt/korzinamarket`; gateway обновляется отдельно. Перед выпуском сохраняются чистый Git baseline, SHA/ветка, systemd overrides, DB custom dump, runtime с зависимостями, исходники и uploads. Проверяются gzip/tar, SHA256 и полное восстановление дампа в отдельный tmpfs PostgreSQL. Существующие units/overrides не заменяются.

API собирается отдельно от работающего runtime; короткая остановка только shop-api нужна для переключения готового dist и конфигурации. Web и туннель сохраняются. На ошибке вернуть прежний SHA через обычный `git switch`, восстановить API dist и прежний env, запустить сервис и повторить health. При откате UI база не восстанавливается: схема и бизнес-модель не меняются, новые заказы сохраняются. Gateway откатывается своим архивом dist.

Полное аварийное восстановление БД из проверенного dump — отдельная операция: остановить писателей, сверить необходимость потери более новых данных, восстановить в новую БД, проверить и только затем переключать DATABASE_URL. Не восстанавливать поверх работающей БД автоматически.
