## Контролируемое сравнение

Chromium, 10 Мбит/с, задержка 60 мс, высота 950 px, DPR 1; CPU ×4 на 320/390 и ×1 на 768/1440. Каждый запуск имеет отдельный профиль, очищенный cache и новые image URLs; начальный cache отключён, при прокрутке обычный cache включён. Одна фотография 324254 байта, 240 синтетических товаров. API/Nitro доступны только через localhost; внешние fetch Nitro запрещены.

Для сравнения сетевой политики fixture возвращает первую страницу с `nextCursor=null`: набор фото фиксирован на 24, исходные размеры не меняются. Это предотвращает незаметный запуск следующей страницы при скачке вниз. Реальные бесконечный/виртуальный список, поиск, фильтры, категории и возврат проверены отдельно на всех 240 товарах. Три последовательных повтора каждого кандидата на каждую ширину; порядок в каждом круге: текущий → один high → адаптивная дистанция. Таблицы ниже — медианы.

Прототипы меняют только fixture HTML/браузерные атрибуты/наблюдатели, без изменения production-компонентов:

- Текущий PR: четыре `eager/high`, остальные lazy/async, preload 3000 px.
- Один high: те же четыре eager и такое же decoding; high только у первого фото. Element LCP во всех контролируемых прогонах — первое фото, URL fixture=0. SSR-бюджет записан в JSON (4 eager / 20 lazy / 1 high).
- Адаптивный: четыре high; начальная дистанция `clamp(1250, 2 × viewport height, 3000)` (1900 px здесь). При скролле направленный lookahead `clamp(1250, viewport height + скорость × 1500 мс, 3000)`, обновление через rAF. Учитывает viewport/направление/скорость, не предполагает достоверность navigator.connection.

В финальном мобильном контроле он исключён. Поле requested там 0 означает, что этот счётчик не запрашивался; completed и imageBytes измеряются по ResourceTiming.

Во всех трёх политиках после полного просмотра фиксированной страницы загружено 24 фото / 7,79 МБ. Один high не показывает устойчивого выигрыша по четырём ширинам. Адаптивный вариант экономит ранние мобильные байты, но в основном протоколе увеличивает ожидание после скачка примерно на секунду; при одинаковом моменте старта ухудшение также сохраняется: +648/+316 мс на 320/390. Поэтому оба прототипа отклонены; результаты не обосновывают изменение реализации.

В длинном списке observer не может предзагружать отсутствующий DOM. Существующая виртуализация ограничивает его окном около 900 px, даже при rootMargin 3000. Уменьшение стартовой дистанции отнимает запас загруженных фото; увеличение без уменьшения размера файлов увеличивает ранние байты и очередь. Устойчивое улучшение обоих показателей этими изменениями не подтверждено.

### Трафик на 768/1440

В предыдущей unthrottled серии main загрузила 180/216 уникальных фото, PR — 204/240. Рост 7,79 МБ равен 24 дополнительным ответам, а не увеличению оригинала. Набор посещённых/смонтированных строк при автопагинации и скачках не был одинаковым: к нему добавляется preload фото, которые затем пропущены. В новом полном сетевом сценарии обе версии на 768/1440 загрузили 240 фото, по 77,89 МБ. В контроле фиксированной первой страницы обе загрузили ровно 24, по 7,79 МБ. Рост итогового трафика при равном наборе фотографий не воспроизвёлся. В реальном длинном списке prefetch всё равно может передать лишние пропущенные фото.

Первый короткий повторный тест также обнаружил скрытую автопагинацию: на desktop он запрашивал 48–55 фото вместо 24. Его данные сохранены в preliminaryDynamicPage и не используются как контрольная A/B-таблица. Это причина разделения протоколов, а не результат принятой оптимизации.

### CLS на 1440

Первый экран во всех сериях: 0. В полном новом сценарии на 1440 main даёт 0,412, PR — 0,718; 0,408/0,715 соответственно приходятся на фазу pagination. Два крупнейших сдвига PR около 0,339 каждый относятся к `.product-more` (высота около 375 px), который оказывается в viewport при jump-to-bottom и уходит из него при добавлении следующих карточек/смене loading skeleton. На 768 крупнейший источник тот же, высота около 656 px. Sources/previousRect/currentRect и этапы сохранены в JSON. Квадратные области фото не меняют размеры при их загрузке.

Это объясняет место возникновения регрессии, но не доказывает единственную причину разницы таймингов между версиями. ProductMore/useGridWindow не менялись в PR; на main сдвиги тоже воспроизводятся. Требуется отдельный контролируемый frontend-тест размещения loading skeleton и append при видимом sentinel. Списывать результат только на синтетический ввод нельзя: jump-to-bottom специально ставит меняющийся блок в viewport и представляет риск для такого UX.

Здесь CLS — накопленная сумма layout-shift без hadRecentInput, как в исходном harness; это не стандартный максимум session window и не полевая CWV. Для merge нужно устранить/ограничить этот сценарий и подтвердить на измерениях.

## Воспроизведение без изменения исходников

После web build (путь Chromium настроить для своей среды):

```sh
review_dir=$(mktemp -d)
patch -o "$review_dir/review.mjs" apps/web/test/card-images.smoke.mjs < docs/catalog-image-review.fixture.patch
CATALOG_BROWSER_PATH=/usr/bin/chromium IMAGE_TEST_BROWSER_HELPER="$PWD/apps/web/test/browser.mjs" IMAGE_TEST_WEB_DIR="$PWD/apps/web" IMAGE_TEST_NETWORK=1 IMAGE_TEST_RUNS=3 IMAGE_TEST_MEASURE_ONLY=1 REVIEW_FIXED_PAGE=1 node "$review_dir/review.mjs"
```

Для кандидата одного high добавить `REVIEW_PRIORITY=single IMAGE_EXPECT_EAGER=baseline` (изменённый SSR priority-бюджет записывается отдельно; исходный assert четырёх high выключен). Для адаптивного — `REVIEW_ADAPTIVE=1`. Для полного сценария убрать MEASURE_ONLY/FIXED_PAGE. Для main указывать отдельно сохранённый build через WEB_DIR и `IMAGE_EXPECT_EAGER=baseline`.

Для контроля старта скролла применить clock.patch к экспериментальной копии и запускать с теми же fixedPage параметрами. Для Element Timing применить paint.patch к экспериментальной копии:

```sh
patch -o "$review_dir/paint.mjs" "$review_dir/review.mjs" < docs/catalog-image-review.paint.patch
```

Запуск paint.mjs с теми же fixedPage параметрами. Все patch применяются только к копии в temp, не к tracked-файлу. Подготовленные копии проверены `node --check`.

Все исходные результаты: [catalog-image-review-measurements.json](catalog-image-review-measurements.json). Нет production sampling, реальных покупателей, Safari/WebKit, DPR 2/3, real-device CPU или реальных файлов товаров. Синтетический hero-image тяжёлый; результаты описывают этот стенд, а не гарантируют эффект на production.
