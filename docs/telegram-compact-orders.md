# Telegram: компактная корзина, фото и иерархия заказа

Продолжение Telegram Chat UX 2.0. Схема БД, финансовые правила, Mini App и image runner не меняются.

## Корзина и шаг

На товар приходится одна строка `[Название] [−] [+] [✕]`. Название primary, плюс success, удаление danger. Название кнопки ограничено 16 символами, в тексте остаётся полное допустимое название, количество, сумма и цена шага. В Rich количество находится непосредственно над своей строкой кнопок; эти кнопки не дублируются внизу экрана.

Пять товаров на странице сохранены: число рядов управления сокращено вдвое, а высота экрана не увеличена до восьми товарных блоков. Изменение использует текущую страницу и подтверждённый серверный snapshot; удаление последней позиции страницы возвращает на последнюю существующую страницу. Полная очистка требует прежнего подтверждения.

В карточке остаются только минус/плюс одного `product.step`. Быстрых +2/+5 больше нет. Если первое допустимое количество отличается от шага, единственная стартовая кнопка «Минимум: …» выбирает существующий `min`; после этого работает только ±step. Это важно для уже существующих товаров с min>step. Минус, пересекающий min, недоступен; удаление всегда явно доступно через ✕. Последний шаг при min=step удаляется обычным минусом. Целые экземпляры остаются целыми.

## Каталог

До 48 доступных категорий показываются целиком в две колонки без номера страницы. Это максимум 24 ряда категорий плюс навигация, укладывающийся в внутренние лимиты. При большем числе используется пагинация по 24. Старые callbacks продолжают разбираться, номер страницы ограничивается существующим диапазоном. Возврат из товаров использует тот же режим.

На момент read-only аудита сервер содержит 20 доступных категорий — все размещаются в одном сообщении.

## Фотография

Причина отсутствия фото сливы на первом экране: прежний `options.details ? productPhoto(...) : undefined`. Изображение показывалось только после открытия подробностей. Серверный аудит подтвердил существование видимого фото, валидный HTTPS URL магазина, HTTP 200 и `image/webp` (79 848 байт).

Теперь фото включено в обычное открытие и обновление карточки. Описание открывается отдельно и сворачивается в Details. Валидируются ORDER_SITE_URL, HTTPS, origin, допустимый путь, отсутствие credentials/query/hash и локальных адресов. Новые изображения не генерируются.

Из фактического `Message.rich_message.blocks[].photo[]` извлекается подтверждённый `file_id`. Он кешируется отдельно по токену бота и исходному URL на 15 минут, максимум 256 записей. Изменение URL обновляет ключ. Следующие редактирования используют file_id, не требуют повторной загрузки WebP по сети и сохраняют фото. В репозиторий file_id и токены не пишутся.

После подтверждённого отказа cached file_id допускается попытка с исходным URL. Подтверждённый отказ фото допускает Rich без фото, затем обычный текст при необходимости. Timeout/unknown/5xx не запускают слепой повтор или fallback. Отдельные фиксированные причины `no_image`, `invalid_url`, `media_rejected`, `fallback_used` пишутся без URL, IDs, provider body и персональных данных.

## Карточки заказов

`order-rich.ts` строит явные смысловые блоки для существующих customer/staff renderers:

1. Номер и статус заказа.
2. Выделенный способ получения и покупатель.
3. Крупный итог либо явно предварительная/неизвестная сумма.
4. Статус оплаты и фактический прогресс сборки.
5. Выделенное следующее действие; при необходимости — вопросы и расхождения.
6. Разделитель и сворачиваемые расчёт, получение/контакты, товары/дополнительные позиции.
7. Прежние кнопки и callbacks с прежними версиями/правами/подтверждениями.

Схемы проверены по [официальному Bot API](https://core.telegram.org/bots/api#richtextmarked): `marked` содержит type/text; SectionHeading передаётся как type=heading с size1–6. Paragraph, Divider, Details и компактная Table используют документированные поля. Произвольных цветов/CSS нет.

PAID показывает подтверждённую оплату; REPORTED требует проверки и никогда не отображается как получение денег. AWAITING означает ожидание, CANCELED — отмену. Зелёный прогресс показывается только если все позиции PICKED и нет ожидающих решений. MISSING не считается собранным товаром.

В расчёте сохраняются запрошенная сумма, предварительные товары, фактические товары вместе с доп. позициями, скидки, доставка и отдельная сумма платежа за товары. Неизвестные значения остаются «уточняется». Расхождение суммы платежа с существующим `payableGoods` показывается отдельно. Финансовые значения не записываются и не пересчитываются новым UI.

HTML fallback формируется из типизированного RichText, экранируется и выделяет главные поля жирным. Уведомления о результате действия добавляются одновременно к text/Rich/fallback, чтобы новая структура не скрывала подтверждение или сообщение об устаревшей версии.

## Проверка и выпуск

Профильные тесты покрывают четыре кнопки/стили, единицы, минимум/шаг, повторные и конкурентные действия, удаление/страницы, каталоги 1/8/16/48/49/2000, фото/URL/file_id/отказ/unknown, семантические карточки, неизвестные суммы, экранирование и ограничения payload. Примеры 10 карточек покупателя/продавца создаются из production renderers в `work/telegram-ux2-compact/orders.json` через `TELEGRAM_COMPACT_SNAPSHOTS=1`.

Выпуск использует проверенную процедуру прошлого цикла: новый verified backup с восстановлением в изолированную БД, отдельная серверная сборка, короткое переключение только API на конкретный SHA с rollback. Rich allowlist и существующие systemd overrides сохраняются. Gateway менять не требуется.

Визуальная приёмка остаётся проверкой настоящих клиентов: Desktop и Android. Локальные payload/примеры не доказывают переносы и ширину кнопок в Telegram. В текущей среде computer-use runtime не запускается (путь не найден, повтор после reset не помог), поэтому автоматическую визуальную проверку клиента заявлять нельзя. После реальной доставки открыть `/start`, каталог, сливу, корзину и заказ №9, затем `/work`; проверить четыре колонки, фото после нескольких ±, итог/оплату/сборку и Details на обоих клиентах.
