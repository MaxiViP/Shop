# Центр событий KorzinaMarket

Рабочая лента: `/admin/events`. Использует существующую таблицу `AdminChange`,
тот же SQL-триггер и прежнюю очередь Telegram. Нового независимого аудита нет.
Раздел `/admin/activity` остаётся владельцу для проверки доставки уведомлений.

## События и доступ

- Заказы: создание, изменения существующих статусов и доставки, факты сообщений
  и обновления фото без сохранения текста сообщений и файлов в ленте.
- Продажи: существующие записи `OrderPayment`, подтверждение оплаты и завершение заказа.
  Ожидание оплаты и сообщение покупателя об оплате обозначаются своими статусами;
  они не считаются подтверждённой продажей.
- Состав заказа: позиции, количества, фактический вес, цены, итоги и доплаты.
  Это история существующего заказа, а не фискальный чек.
- Продавцы: изменения доступного им каталога; работа с заказами попадает также
  в соответствующую предметную категорию и находится фильтром сотрудника.
- Администраторы: изменения каталога и настроек, включая действия владельца.
- Система: зафиксированные ошибки доставки уведомлений, заявки доставки,
  требующие проверки, и неперехваченные серверные ошибки мутаций HTTP.
  Ошибка операции записывается отдельно от откатившейся транзакции с явной
  пометкой «Операция не выполнена», без текста исключения и тела запроса.

Возвраты денег, фискализация и отдельный количественный складской учёт в текущих
моделях не реализованы. События для этих процессов не создаются. Доступность
товаров фиксируется через существующие поля каталога.

Владелец определяется `ADMIN_PHONE` и видит все события. Назначенные ADMIN
видят общую рабочую ленту. Изменения ролей, паролей, прав на точки, выплаты
партнёрам и проблемы личных уведомлений владельца закрыты от них.
Проверки выполняются в API, фильтрах поиска/сотрудников и SSE. Прежний основной
аккаунт без отдельного пароля также теряет доступ через старую привязку
Telegram после изменения `ADMIN_PHONE`. Продавцам,
покупателям и гостям API ленты недоступен. Управление всеми ролями и правами
на торговые точки доступно только владельцу; запрет действует в сервисе API.

В событиях хранятся идентификатор и снимок роли автора, имя сотрудника либо
обезличенное «Покупатель», источник, операция и разница разрешённых полей.
Пароли, хеши, токены, телефоны, адреса, комментарии покупателей и тела ответов
провайдеров не сохраняются. Длинные строковые значения ограничены 240 символами.
Ошибки Telegram не откатывают бизнес-операции.

## Данные и доставка

Миграция `20261103120000_event_center` расширяет `AdminChange`:
категория, заголовок, снимок роли, видимость, признак уведомления владельца,
ссылки на заказ/товар, ID транзакции и ключ устранения повторов.
Существующая миграция `20261103100000_delegated_admin_activity` сохраняется.
Старые записи сохраняют ID и состояние доставки; их избыточные поля очищаются
тем же разрешающим списком. История до появления журнала не выдумывается.

Триггер пишет событие в одной транзакции с изменением, включая SQL, bulk и
каскады. Откаты удаляют и изменение, и событие. Записи без изменения разрешённых
полей игнорируются. Уникальный ключ исключает повтор одного и того же изменения
в одной операции/транзакции. Повторный HTTP-запрос, реально изменивший данные
ещё раз, остаётся отдельной операцией; существующая идемпотентность бизнес-API
сохраняется.

Telegram владельцу отправляется только для `notifyOwner=true`, то есть о
действиях других ADMIN. Его собственные действия и действия продавцов
сохраняются в ленте без таких уведомлений. UNKNOWN не отправляется автоматически
повторно; владелец может явно повторить отправку в прежнем разделе.

## SSE и история

`GET /api/admin/events` принимает `category`, `actorId`, `orderId`, `from`, `to`,
`q`, `before`. Даты интерпретируются по Москве, конечный день включён.
Пагинация по ID, 40 событий на страницу. Группировка в интерфейсе выполняется
в пределах страницы по операции или заказу. Поиск использует русский полнотекстовый
индекс GIN. Служебные поля очереди и ID транзакций не возвращаются в рабочей ленте.

`GET /api/admin/events/stream` использует HttpOnly cookie и те же фильтры.
SSE сообщает количество новых видимых событий; интерфейс загружает актуальную
страницу из API. На странице истории новые события не прерывают чтение.
`Last-Event-ID` поддерживает переподключение; курсор подписан `AUTH_SECRET`,
привязан к пользователю, правам и фильтрам и действует семь суток.
После истечения срока/невалидного курсора приходит `reset`, и клиент обновляет
ленту. Старые события доступны через пагинацию в пределах срока хранения.

Курсор основан на видимости PostgreSQL snapshot, а не только максимальном ID:
поздний commit с меньшим ID также учитывается. Используется ID верхней транзакции
`pg_current_xact_id()`, а не `xmin` строки/ID подтранзакции. Описание функций:
[PostgreSQL transaction snapshots](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT).

Проверка сессии и актуальной роли повторяется каждые три секунды. Отзыв сессии
или прав закрывает поток; закрытые данные не отправляются в SSE даже владельцу —
только счётчик в его области видимости. Не более трёх потоков на пользователя
в одном API-процессе. Поток переподключается через 30 минут, медленные клиенты
отключаются. БД опрашивается каждые три секунды, запросы одного потока не перекрываются.
Ответ содержит `X-Accel-Buffering: no`, heartbeat/sync поддерживает соединение
активным. Проверить поведение reverse proxy следует при выпуске.

## Хранение и выпуск

Индексы: транзакция, категория/видимость, заказ, сотрудник, дата, полнотекстовый
поиск и прежние индексы очереди. Нет сохранения файлов, полных запросов и
неограниченных provider payloads. По умолчанию история хранится 180 дней;
`EVENT_RETENTION_DAYS` допускает 30–3650. Раз в час удаляется не более 1000 старых
завершённых записей. Неразрешённые отправки PENDING/SENDING/UNKNOWN/FAILED
автоматически не удаляются. Их объём и свободное место VPS нужно контролировать;
конкретный объём зависит от числа операций.

Перед выпуском: проверенный backup, обе миграции на staging/копии данных,
проверка Telegram и SSE через reverse proxy, затем отдельное разрешение владельца
на production-миграции и переключение сборки. Откат кода не требует удаления
добавленных таблиц/колонок. Не восстанавливать старый dump поверх новых заказов.

Проверки запускаются только с изолированной локальной БД `korzina_e2e*`.
Браузерные сценарии используют локальные fixtures и отдельный headless Edge;
не подключаются к рабочему браузеру пользователя и production.
