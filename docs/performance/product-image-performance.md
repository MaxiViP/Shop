Дата измерений и проверки артефактов: 2026-10-15. Исходная ревизия: `2f24016`.
Отчёт составлен из сохранённых результатов в `work/product-image-performance/`.
При восстановлении работы выполнялись только чтение JSON/логов и проверка их

В Lighthouse каталога варианты уменьшили медиану image bytes на 87,44%,

Performance снизился, TBT вырос.

## Причина `57 !== 48`

`run-A.log` фиксирует падение в прежней редакции `browser.mjs:161`.
В текущем файле assertion количества товарных URL находится на строке 186:
номер строки в старом stack trace не соответствует текущему исходнику.

Во всех сохранённых `A-cdp-*.json` массив `network` содержит ровно 57 уникальных
источников типа Image:

| Область подсчёта после прокрутки | A | B |
| --- | ---: | ---: |
| HTTP-изображения `/uploads/products/` | 48 | 48 |
| HTTP-логотипы `/img/logo/empty-cutout.webp`, `/img/logo/full-cutout.webp` | 2 | 2 |
| Встроенные SVG `data:image/svg+xml` | 7 | 0 в сохранённом массиве |
| Всего записей `network` / `allImageRequests` | 57 | 50 |
| Всего HTTP-изображений после исключения `data:` | 50 | 50 |

Таким образом, `57 = 48 + 2 + 7`. Сравнение всех источников изображений с числом
товаров использовало неверную область подсчёта. Все 48 товарных URL уникальны,
завершены с HTTP 200, без сетевых ошибок. Признаков повторных товарных загрузок
в этих данных нет; это assertion измерительного сценария, а не установленная
ошибка магазина.

Текущий collector сначала ограничивает сеть HTTP(S), а assertion — путём
`/uploads/products/`. Сохранённая A-серия ещё включает `data:`, B-серия уже
исключает их. Поэтому сырые `imageRequests` 32 → 26 и `allImageRequests`
57 → 50 нельзя выдавать за сокращение HTTP-запросов: сопоставимые количества
равны 26 до прокрутки и 50 после неё, включая два логотипа. Семь `data:` записей
имеют `transferred: 0`, поэтому итоги в байтах не искажены.

## Lighthouse: каталог и главная

Lighthouse 13.5.0, Edge/Chromium 155 (браузер в functional-отчётах
`155.0.4283.45`), Windows. Каждый запуск использовал свежий профиль и сброс
хранилищ, mobile viewport 390 × 844, DPR 2. Метод — `simulate`: RTT 150 мс,
throughput 1638,4 Kbps, CPU ×4; дополнительные настройки сети:
`requestLatencyMs: 562.5`, download 1474,56 Kbps, upload 675 Kbps.
Это отдельная серия с симулированными временными метриками.

В таблицах — медиана трёх запусков, в скобках min–max; одинаковые значения
показаны без диапазона. Время — мс, bytes — целые байты, Δ = B − A по
неокруглённым медианам. Каждая метрика агрегируется отдельно: строка медиан
не представляет один выбранный запуск.

Performance берётся из `categories.performance.score × 100`, FCP/LCP/TBT/CLS —
из соответствующих `audits.*.numericValue`. Image bytes — только из этого же
Lighthouse-отчёта: `audits.resource-summary.details.items`, строка
`resourceType: image`, поле `transferSize`. Суммы сверены с `network-requests`.
Это весь учтённый трафик изображений навигации, включая логотипы и hero на
главной, а не только товарные фотографии или байты до LCP.

## CDP: каталог и scroll readiness

Эта серия использует фактическое CDP throttling: CPU ×4, latency 150 мс,
download 200 000 B/s, upload 93 750 B/s, cache disabled, свежий context;
viewport 390 × 844, DPR 2. Lighthouse-оценка Performance и TBT для неё
не вычислялись. Массив long tasks не используется как замена Lighthouse TBT.

Начальный снимок снимается после hydration, загрузки изображений 24 карточек
и дополнительной секунды ожидания. FCP/LCP берутся из paint/PerformanceObserver,
CLS — сумма сохранённых сдвигов без recent input до прокрутки. Эти значения
имеют другую методику и окно наблюдения, чем Lighthouse, и не объединяются
с его результатами даже при совпадении отдельных чисел.

| Метрика CDP, медиана (min–max) | A | B | Δ |
| --- | ---: | ---: | ---: |
| FCP, мс | 8 068 (7 976–8 096) | 6 596 (6 596–6 808) | −1 472; −18,24% |
| LCP, мс | 8 068 (7 976–8 096) | 6 596 (6 596–6 808) | −1 472; −18,24% |
| CLS | 0,0000103741 | 0,0000103741 | 0 |
| Image bytes до прокрутки, HTTP | 3 972 678 | 498 936 | −87,44% |
| Из них 24 товарных изображения | 3 892 584 | 418 842 | −89,24% |
| Image bytes после загрузки всех 48 товаров, HTTP | 7 954 579 | 926 221 | −88,36% |
| Из них 48 товарных изображений | 7 874 485 | 846 127 | −89,25% |
| Scroll readiness (`scroll.ms`), мс | 14 692 (13 974,6–15 240,8) | 2 601,7 (2 548,1–2 609) | −12 090,3; −82,29% |
| Появление 48 товаров (`scroll.feedMs`), мс | 1 072,7 (982,4–1 072,9) | 1 167,3 (1 132,6–1 179) | +94,6; +8,82% |

`scroll.ms` начинается с прокрутки вниз, включает ожидание `loadedCount >= 48`,
повторную прокрутку к новому низу страницы и ожидание загрузки видимых там
изображений (`complete && naturalWidth > 0`) с двумя animation frames до и
после проверки. Во всех шести снимках видимы четыре загруженных изображения.
Это готовность нижнего viewport, а не время загрузки всех 48 фотографий.
Итоговые `allImageBytes` снимаются позже, после отдельного ожидания всех картинок.

Bytes — сумма `Network.loadingFinished.encodedDataLength` (`transferred`),
включая HTTP-заголовки, не размер файлов на диске. Во всех шести JSON суммы
согласуются с `headersBytes + sum(data[].bytes)`. До прокрутки товарные запросы
выделены из полного `network` по 24 `images[].currentSrc`; после неё — по
`/uploads/products/`. Два логотипа добавляют одинаковые 80 094 байта в A и B;
этим также подтверждается сопоставимость сохранённых `imageBytes`.

У A отсутствуют `navStart`, `initialNetwork`, `initialHttp` и
`totalBytesBeforeLcp`, которые уже есть у B. Поэтому полный трафик до LCP
для пары A/B — **N/A**. Сохранённое `imageBytesBeforeLcp` описывает только
изображения и не заменяет полный трафик. Текущий `summarize.mjs` требует
`totalBytesBeforeLcp` для обеих серий и без адаптации не подходит к этим A JSON;
таблицы рассчитаны напрямую из доступных полей, без заполнения пропусков
значениями Lighthouse.

## Сохранённые функциональные проверки

`A-functional.json` и `B-functional.json` имеют `status: passed`: по 20 страниц
и 20 действий на режим. Проверены `/catalog`, `/`, `/favorites`, карточка товара,
добавление в корзину, переключение темы, переходы и выбор фотографии галереи.
Runtime errors, hydration warnings и внешние браузерные запросы — 0 в обоих
functional-отчётах и всех CDP-снимках. Все записанные изображения завершили
загрузку с положительным `naturalWidth`.

Миниатюры галереи выбирают 192, основная фотография сохраняет оригинал.
Сопоставлены 590 измерений ширины/высоты изображений A/B: максимальная разница
геометрии 0 px. Это сохранённая матрица одного Chromium/Edge, без данных
Firefox/Safari и реальных устройств.

Оба integration-отчёта подтверждают каталог, detail и авторизованное избранное
через настоящий API, SHA-256 48 оригиналов и неизменность image storage после
HTTP-чтений. В B дополнительно сохранены 144 успешных ответа вариантов.
`B-authenticated.json` подтверждает избранное и изменение корзины через обычную
DB-сессию без клиентской цены в запросе. Отдельного `A-authenticated.json` нет;
авторизованный UI-сценарий A не отмечается как пройденный.

`missing-ready.json` подтверждает исключение отсутствующего READY из API,
сохранение остальных метаданных, HTTP 307 к оригиналу для старого variant URL,
HTTP 200 оригинала и восстановление тестовых файлов.

## Границы результата

Это последовательная локальная серия A, затем B, по три измерения на страницу,
без рандомизации и доверительных интервалов. Убедительно подтверждены снижение
трафика одинаковых товарных фотографий каталога и ускорение готовности нижнего
viewport на этом стенде. Каталог улучшил Lighthouse LCP и медиану Performance;
главная улучшила LCP, но её score/TBT не позволяют заявить об общем ускорении.
Полный трафик до LCP и scroll readiness главной имеющимися парными данными
не установлены.

В рамках восстановления изменена только документация. Повторных длительных
тестов, push, merge, deploy и production backfill не выполнялось.
