# Финальная проверка назначаемых администраторов и Центра событий

## Этап: Telegram gateway unit — диагностика (2026-11-03)

Область текущего этапа: только Telegram gateway. Сохранённые успешные API E2E
(538/538), API unit (2038 passed, 20 skipped) и Web unit (452/452) не повторяются.
Build, browser smoke, production-миграции, деплой и коммиты не выполняются.

- Исходный лог: `work/delegated-admin/event-center-unit-final.log`.
- Упавший тест: `accepts a JSON UTF-8 charset but no compressed input`.
- Файл: `apps/telegram-gateway/test/server.spec.ts`, исходная строка 182;
  вызов `fetch` в помощнике `send`, исходная строка 22.
- Ошибка: `TypeError: fetch failed`, причина `Error: bad port`.
- Тестовый URL: `http://127.0.0.1:<OS-assigned-port>/v1/customer/sendMessage`.
  Порт выбирается через `listen(0)`; конкретный порт исходного сбоя не записан.
  Production-порт gateway — 18080, к выбору тестового порта не относится.
- Окружение диагностики: Windows, Node.js v24.20.0, встроенный Undici 7.29.0,
  pnpm 11.24.0. Версия Node соответствует требованию проекта >=24 <25.
- Встроенный код Undici возвращает `bad port` для URL с портом из списка
  запрещённых Fetch портов до установления соединения. Максимальный порт
  в этом списке в проверенной версии — 10080.
- Отказ Fetch на порту 10080 воспроизведён с наследуемыми proxy-переменными
  и после их удаления в дочернем процессе. Значения proxy и секреты не сохраняются.
  HTTP_PROXY/HTTPS_PROXY настроены; NO_PROXY включает localhost, IPv4/IPv6 loopback.
  NODE_USE_ENV_PROXY и NODE_OPTIONS не заданы. Переопределений Fetch/dispatcher
  в gateway-тестах не найдено.
- Классификация: нестабильный выбор порта в тестовой инфраструктуре, а не ошибка
  обработки JSON/compression в реализации gateway. Исходный номер порта установить
  по сохранённому логу невозможно; механизм отказа подтверждён воспроизведением
  и встроенным исходным кодом Fetch.
- Отдельное ограничение текущей песочницы: соединения с локальным сервером
  возвращают EACCES как для Fetch, так и для node:http на обычном порту.
  Это отличается от исходного `bad port`; для проверок нужен loopback-доступ.

Минимальное исправление ограничено тестовым помощником: закрывать listener с
портом <=10080 и выбирать случайный порт в диапазоне 49152–65535. Коллизия
EADDRINUSE или EACCES повторяет только bind; всего не более 10 попыток, ошибка
последней попытки не скрывается. Бизнес-запросы не
повторяются. Добавлен регрессионный тест с принудительным результатом первого
выделения порта 10080. Проверки запрета сжатия, маршрутов, лимитов, токенов,
редиректов и повторных отправок не ослабляются. Production-код не изменяется.

Первый адресный прогон показал, что повторение `listen(0)` может десять раз
подряд возвращать низкие порты. Поэтому повторный bind явно выбирает высокий
диапазон; ошибка записана в `work/delegated-admin/gateway-targeted-final.log`,
дальнейший успешный результат будет сохранён отдельно. Это исправляет
недостаток первого варианта помощника, а не меняет критерии теста.

Первый полный gateway-прогон: 87 passed, 1 failed. Windows отклонила bind
явно выбранного высокого порта с EACCES. Помощник теперь выбирает другой
порт и при EACCES, сохраняя ограничение числа попыток. Добавлены отдельные
регрессионные сценарии коллизии EADDRINUSE и недоступного порта EACCES.
Исходный результат сохранён в `work/delegated-admin/gateway-suite-verified.log`.
