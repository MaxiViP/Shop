# Telegram UX 3.4 — покупка из категории

Проверки парной галереи (2026-10-24): Telegram/CartService 861 passed, Linux screen regressions 64 passed, полный Telegram PostgreSQL E2E 185 passed / 0 failed / 0 skipped одним финальным прогоном в изолированной БД. API typecheck (оба конфига), lint, build и diff-check прошли. Реальный preview из отдельной сборки: send/edit HTTP 200, 4 Collage по 2 фото, 16 основных кнопок в индивидуальных подписях; байты каждого JPEG сверены с product ID. Повторное открытие использовало file_id без загрузок. Корзина, заказы и адреса не изменились. Журналы: `work/telegram-ux34-pairs/`. Ширина кнопок и внешний вид на клиентах по API не подтверждаются.

После `6dbafae` восстановлен строго парный [Collage](https://core.telegram.org/bots/api#inputrichblockcollage): две фотографии 4:3. Название/цена и «Добавить в 🛒» входят в `Photo.caption.text` как две нативные [RichTextButton](https://core.telegram.org/bots/api#richtextbutton) конкретного фото. Они используют исходные product ID, контекст и revision. При наличии товара `−`/`+` идут следующим уровнем той же подписи. Независимый общий ряд кнопок под коллажем не создаётся; Rich renderer не дублирует действия из подписей обычной клавиатурой.

Подтверждённое количество остаётся в кнопке названия/цены. Нечётная последняя позиция дополняется нейтральным слотом 4:3 без действий; отсутствующее фото заменяется таким же слотом с собственными кнопками и пояснением. Заглушка JPEG создаётся один раз в памяти, не меняет оригиналы или image runner и не запрашивается по внешнему URL. Длинные совпадающие названия различаются стабильным product ID. Фото остаются без нарисованных подписей. Сохраняются 8 товаров на странице, JPEG 4:3 и отдельный bot-specific кеш file_id миниатюр/полноразмерных карточек. При отказе медиа подписи с кнопками сохраняются в Rich Paragraph; HTML fallback использует те же строки клавиатуры. Нет fallback с одной фотографией в ряду.

Прямое добавление использует существующие CartService и adjust: компактный внутренний callback `s:j` имеет ту же структуру и длину, что `s:u`, и добавляет только признак возврата в категорию. Парсер требует конкретную категорию и страницу. Существующие callback товара/корзины/быстрых покупок совместимы. Первый шаг — актуальный min, последующие — step; недопустимое уменьшение и предел переменного веса не предлагаются. Сервер повторно проверяет единицу и правила продажи. При устаревшей revision выполняется только чтение, при потерянном результате нет автоматического повторения мутации. Подтверждение и новые кнопки строятся по возвращённому CartService snapshot. Пагинация сохраняется; уведомление заменяется и исчезает при обычном открытии страницы.

Карточка товара показывает явное первое действие с количеством и предварительной/неизвестной стоимостью. После добавления основные кнопки называются «Уменьшить»/«Увеличить» и находятся в одной строке. Полное количество и серверная стоимость выделены в Rich и HTML. Ценовая дельта не добавляется к подписи кнопок изменения количества. Предварительные значения и неизвестная стоимость не превращаются в фактическую цену или ноль.

Без подтверждённого собственного Telegram-телефона категория читает только публичные товары: вместо мутации — существующее подтверждение телефона. Сохранённый callback также проходит авторизацию заново. HTML fallback содержит те же product ID, ревизии и строки кнопок без повторного текстового списка. Ошибки Telegram обрабатываются существующим транспортом отдельно от бизнес-операции.

[InputRichBlockPhoto](https://core.telegram.org/bots/api#inputrichblockphoto) не предоставляет `callback_data` на самом изображении, но его `caption.text` поддерживает RichTextButton. Реальный probe Telegram подтвердил HTTP 200, 4 Collage по 2 фото и по 2 кнопки в каждой из 8 подписей с правильными product ID. API не возвращает пиксельные координаты и не позволяет задать ширину кнопок; одинаковая ширина и видимость подписей под миниатюрами не объявляются гарантированными. Нативные Desktop/Android требуют пользовательской визуальной проверки конкретного preview до production-деплоя.

CartService, расчёты/скидки, checkout, оплата, взвешивание, STAFF, Rich policy, глобальные меню команд, Mini App, Prisma, image runner и Web не изменяются. Выпуск только API с проверенным backup/откатом и сохранением текущего глобального Rich.

Неподтверждённый аккаунт должен получить запрос телефона вместо изменения корзины.
