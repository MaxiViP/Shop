## Реализация

- `Card.vue`: `loading="eager"` + `fetchpriority="high"` для ведущих фото; остальные `loading="lazy"`; `decoding="auto"` сохраняет прежний выбор браузера для первых четырёх фото; остальные используют `async`. Ближайшие фото предварительно загружаются в зоне 3000 px после гидратации, с сохранением обычного приоритета.
- `Grid.vue`: первые четыре карточки первой группы получают приоритет. Индекс включает смещение виртуального окна, поэтому новые страницы и удалённые группы не получают новый eager-бюджет.
- `catalog/View.vue`, `favorites.vue`: бюджет включён только для первой группы. Избранное использует тот же компонент карточки; его компактные пропорции не меняются.
- `card-images.smoke.mjs`: локальные fixture/Nitro/Chromium, без backend/БД, SSR и реальные браузерные проверки.
- `catalog-images.yml`: отдельный CI для typecheck/lint/build, 58 профильных тестов и четырёх браузерных сценариев.

Квадратная область каталога, object-fit: contain, переходы, товарные данные и обработчики сохранены. Фотографии корзины и галерея страницы товара не меняются. Src остаётся в SSR HTML. Один одноразовый IntersectionObserver на отложенное фото отключается при попадании в preload-зону, смене URL/ref или уничтожении карточки. Нет новых зависимостей или пустых src. При CSR атрибуты priority/loading/decoding устанавливаются перед src; это проверяется браузерным тестом.

## Почему четыре, а не семь или один

На мобильных 320/390 × 950 px видимы четыре изображения. Эксперимент с eager=7 загрузил 10 фото до первого скролла, как и eager=1: браузер сам загружает ближайшие lazy-фото заранее. Семь не дали экономии запросов.

Eager=1 на 320 px сохранил LCP в пределах шума (1012 → 1020 мс), но время готовности всех четырёх видимых фото ухудшилось (873 → 1305 мс). Поэтому выбран бюджет 4: два мобильных ряда начинают загрузку из SSR без ожидания определения положения lazy-изображений. Окончательная версия сохраняет auto-декодирование критических фото; async используется для остальных.

На desktop все видимые соседние фотографии native lazy загружает автоматически; четыре width-профиля проверены. При очень высоком экране число видимых карточек может быть больше четырёх — это не запрет на загрузку остальных видимых lazy-фото. Зону native lazy задаёт браузер; приложение добавляет контролируемый lookahead 3000 px после гидратации. Чистый native lazy на ограниченной сети увеличивал ожидание при мгновенном переходе с ~1,3 до ~3,2 с. Добавлена зона 3000 px (1,5 с при 2000 px/с). Она уменьшает задержку до ~1,6 с, но требует больше ранних запросов: 20/18 на мобильных вместо 10. Это сознательный компромисс, а не максимальная экономия счётчика. В длинном виртуальном списке lookahead также ограничен уже существующим DOM-окном (~900 px); его алгоритм не менялся.

Ветка `audit/catalog-image-loading-20261013` (`ffa3a350`) исследована, её native lazy/async подход использован и уточнён измерениями. Ветка не переписана и не объединена: её двухфайловый предварительный diff заменяет этот PR, отдельно применять его повторно не следует.

### Ограниченная сеть, 390 px, CPU ×4

Три повтора; 10 Мбит/с, задержка 60 мс. Медианы: LCP 2860→2912 мс; load всех видимых фото 2899→2960 мс. Разница около 2%, улучшение LCP на этой сети не доказано. До первой прокрутки фактически завершены 18→16 фото (5,84→5,19 МБ); часть eager-запросов ещё может находиться в очереди браузера. Худшее ожидание при мгновенных скачках: медиана 1167→1592 мс. Это оставшаяся регрессия относительно полностью eager baseline, хотя гораздо лучше чистого native lazy (~3186 мс). Варианты 2000/2500/3000 px и изменение приоритета исследованы; повышение приоритета всей preload-зоны ухудшало LCP и не включено. Нельзя гарантировать отсутствие поздних фото при мгновенном скачке за пределы lookahead. PR должен оставаться draft до принятия этого компромисса либо следующего отдельного этапа размеров.

## Воспроизведение

После web build:

```sh
CATALOG_BROWSER_PATH=/usr/bin/chromium IMAGE_TEST_RUNS=1 node apps/web/test/card-images.smoke.mjs
```

По умолчанию проверяются 320/390/768/1440 px; три повтора. `IMAGE_TEST_MEASURE_ONLY=1` — короткие измерения, `IMAGE_TEST_NETWORK=1` — 10 Мбит/с/60 мс, `IMAGE_TEST_WIDTHS=390` — один профиль. `IMAGE_TEST_WEB_DIR` может указывать на отдельно сохранённый baseline build; `IMAGE_EXPECT_EAGER=baseline` отключает только проверки новой SSR image-политики. Screenshot/HTML/results сохраняются в временную директорию или заданный `IMAGE_TEST_ARTIFACT_DIR` (её нужно создать заранее). Nitro и fixture работают только на 127.0.0.1; исходящий fetch Nitro заблокирован, proxy проверяет локальный origin. Нет backend startup или DATABASE_URL.
